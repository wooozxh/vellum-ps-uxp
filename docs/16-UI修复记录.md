## 二、8 条缺陷 → 4 个根因

修之前先把 8 条归堆。**表面看是 8 个独立小问题，实际只有 4 个技术根因**，
其中 3 个是「我的写法在 UXP 里不成立」：

| 根因 | 中招的条目 | 一句话 |
|---|---|---|
| **R1 · UXP 的 SVG 不做 `fill`/`stroke` 继承** | 2.1（✕ 看不见）、2.2（返回箭头看不见）、1.4（四项 icon 看不见）、1.1/1.3（hero 渲染成**黑色圆角方块**） | 父节点写 `fill="none" stroke="currentColor"` **传不下去**，子元素退回 SVG 初值 `fill:black; stroke:none` |
| **R2 · `<button>` 在 UXP 里不吃 `display:flex`，且强制 `text-align:center`** | 1.4（文字居中，改不动）、1.1（返回键隐掉后**留下空位**） | 拿 `<button>` 当布局容器 = 必翻车 |
| **R3 · `display:inline-flex` 不可靠 + flex `gap` 不生效** | 1.2（圆点与文字**重叠**、垂直没对齐） | 间距必须落成 `margin`，不能指望 `gap` |
| **R4 · 纯 CSS 数值问题** | 2.1（行距太紧） | 没有坑，纯粹没调够 |

**这一步的收益**：如果按 8 条各修一遍，会写出 8 处局部补丁；
按 4 个根因修，改的是 `lib/icons.js` 的绘制层、`index.html` 的布局纪律、和一处 CSS 数值。

## 三、逐条修法（含真机数字）

### R1 · SVG 绘制属性逐元素写死

新增 `icons.js` 的 `applyPaint(node, mode, sw)`，**对根节点和每一个子元素都调一遍**：

```js
function applyPaint(node, mode, sw) {
  if (mode === "fill") {
    node.setAttribute("fill", "currentColor");
    node.setAttribute("stroke", "none");
    return;
  }
  node.setAttribute("fill", "none");
  node.setAttribute("stroke", "currentColor");
  node.setAttribute("stroke-width", sw);
  node.setAttribute("stroke-linecap", "round");
  node.setAttribute("stroke-linejoin", "round");
}
```

顺序上**先补默认、再写规格 attrs**（后者可覆盖）。另修两处细节：

- `del` 图标的描边从 1.5 加到 **1.9**（✕ 在 18px 的深色小圆底上要够粗才看得清）
- `alert` 图标的小圆点**显式写** `fill:currentColor; stroke:none`（它是唯一的实心元素）

**真机取证**（`selfcheck S14`）：

```
S14 图标逐元素自带 fill/stroke（UXP 不做继承）  ::  共 18 个图标　缺属性 0
```

### R2 · 全面弃用 `<button>`，改 `div[role="button"]`

- 外壳返回键、环境 chip、首页四个功能行、调色板的「存为我的颜色」，**全部**改 `div[role="button"] tabindex="0"`
- `index.html` 里把 `button {}` 选择器换成 `[role="button"] {}` 做样式复位
- 返回键「空位」问题：**不是**把按钮删掉，而是 `.back.is-off { display:none }` —— 隐藏时**不占位**

**守护**：离线回归断言 **3c「不使用 `<button>` 承载布局」**（首页 button = 0、整页 button = 0）。

### R3 · 间距一律用 `margin`，绝对定位排布首页行

`.bar-chip` 从 `inline-flex + gap` 改成：

```css
.bar-chip { display: flex; margin-left: 8px; height: 20px; line-height: 20px; }
.led      { margin-right: 6px; }   /* 不再依赖 gap */
```

`.navitem` 干脆**完全绝对定位**，不靠流式排版：

```css
.navitem   { position: relative; height: 54px; padding: 0 34px 0 48px; }
.ni-ico    { position:absolute; left:12px; top:14px; width:26px; height:26px; }
.ni-name,
.ni-desc   { text-align: left; }        /* 显式写，抵抗继承来的居中 */
.ni-key    { position:absolute; right:34px; }
.ni-arrow  { position:absolute; right:11px; }
```

**真机取证**（`selfcheck S13`，全用 `getBoundingClientRect`）：

#### ⚠️ 号位 chip「↑1…↑4」是**视觉占位**，不是真快捷键

必须说清楚，避免误解：**UXP 面板里的导航项绑不了快捷键**。

- `manifest v5` 的 `command` 支持 `shortcut: { win, mac }`，但**必须含 Ctrl**，
  且**只支持字母 / 数字**（方向键、标点、F1–F12 都不支持）
- 更关键：**只对 `command` 生效，Panel 内部的列表项绑不上**

所以「↑1…↑4」只能表达「这是第 1 个入口」的序列感。**如果看着别扭，说一声去掉即可**
（`index.html` 里 `.ni-key` 一行 CSS + `index.js` 里发号位那两行）。

> **📌 v0.2.2 更正（见 `docs/17` §3.6）—— 上面这段只说对了一半，别照着它做计划。**
> 「`manifest v5` 的 command 支持 shortcut」这句**在语法层面成立**（且真机 `Validate` 会通过），
> 但那份文档是 **Premiere / InDesign / XD** 的。**Photoshop 到底认不认？**
> Adobe 官方论坛（Photoshop / UXP 分区）从 2021 问到 **2024**，答案一直是 **"Not yet possible"**；
> Adobe 员工 2024-06 明确说「**UXP 核心 API 不支持键盘快捷键**」，社区替代方案是「录成动作再绑 F 键」。
> → 结论：本项目里那条 shortcut 是 **best-effort**（语法合规、无害，但很可能被 PS 忽略），
> **不能对外承诺"按 Ctrl+Alt+F 就能填充"**。真正可自证的是面板内的 **`Alt+左键`**（走我们自己的处理器）。
> 教训：**"某份文档写了" ≠ "我们这个宿主支持"** —— 查能力时先确认文档属于哪个宿主。

## 四、🩸 本轮最值钱的发现：**探针自己是错的**

修完 UI 去复验，`selfcheck` 报 **15/15 全 PASS**。但同一份日志里有个东西不对：

```
NO  布局测量  ::  width:100px → rect.width=0px　offsetWidth=0
```

一个 `width:100px` 的块，量出来是 0px。**而这已经不是第一次了** —— 上一轮探针就报过
「CSS 变量不支持 / letter-spacing 不生效 / transform 无效」，全是 `0`。
当时的解释是「离屏容器 `left:-9999px` 被 UXP 裁剪（culling）」，
于是我把容器改成 `left:0 + height:1px + overflow:hidden`（可见但被裁切）—— **改完仍然是 0**。

### 真正的判别实验

同一轮里，`computed` 类探针（outline / box-shadow / linear-gradient）返回的是**正确值**。
→ 说明 **style 确实应用了**，问题不在「样式没生效」，而在「**量不到几何**」。

而自检 `S13` 能量到真实几何（行高=54、图标=26x26）。两者的差别只有一个：

| | 量的时候 | 结果 |
|---|---|---|
| `S13` | 元素**早就在 DOM 里**，中间隔了若干 `await` | ✅ 真实值 |
| 探针 | 刚 `appendChild` 完，**同一个同步块里**立刻量 | ❌ 全 0 |

**结论：UXP 的布局是异步/延迟的。** 同步 `appendChild` 后立即
`getBoundingClientRect()`，拿到的是「**尚未参与布局**」的 0，而不是「该特性不支持」。

### 修法：先建 → 让出两帧 → 后量

```js
function settle() {
  return new Promise((resolve) => {
    // 连让两帧：第一帧常常只是"标记脏"，第二帧才是真正的布局结果
    requestAnimationFrame(() => requestAnimationFrame(() => resolve()));
  });
}
```

配套把 `cssprobe.run()` **从同步改成 async**（`selfcheck S9` 已改 `await`）。

### 再加一条「基座自证」探针（⓪ harness）

不只修，还要**防止再犯**：新增第 0 项探针，不测任何 CSS 特性，
只测「**这套量法本身靠不靠得住**」——同一元素量两次（同步 vs 让帧后）：

```
OK  测量基座自证（几何类结论的前提）
    ::  同步量=0px　让出两帧后=120x12（期望 120x12）　容器宽=320px
    → 基座有效，几何量可信（并证实：UXP 布局异步，同步量必为 0）
```

并且**基座一旦失效，所有 `via="几何实测"` 的结论会自动追加「⚠️ 基座未参与布局，此结论不可信」**。
宁可承认测不准，也不给假阳性。

### 修正后的真机结论：**9/14**（原为 4/13）

| 特性 | 旧结论 | **修正后** | 说明 |
|---|---|---|---|
| CSS 自定义属性 `var()` | ❌ | **✅** | `--probe-w:137px` → 实测宽 **137px** |
| `letter-spacing` | ❌ | **✅** | 0px→93px；10px→**193px**，**差出 100px** |
| `transform` | ❌ | **✅** | `translateX(30px)` → 实测 **+30px** |
| `rect` / `offset*` 布局测量 | ❌ | **✅** | rect.width=100、offsetWidth=100、**offsetHeight=10、offsetLeft=40、offsetTop=7** |
| `outline` | ✅ | ✅ | `outlineWidth="2px"` |
| `box-shadow` | ✅ | ✅ | 需 `CSSNextSupport` flag |
| `linear-gradient` | ✅ | ✅ | PS 26.1 / UXP 8.1 起 |
| SVG 命名空间 | ✅ | ✅ | `namespaceURI` 正确 |
| **flex `gap`** | ❌ | **❌ 确认不支持** | 两子项各 20px + gap 10px → 起点差 **20px**（=只有宽度，没有 gap） |
| **SVG 子元素继承 fill/stroke** | ❌ | **❌ 确认不继承** | 子 computed `fill="black" stroke="none"` |
| **伪元素 `::before`** | ❌ | **❌ 确认不支持** | content = `"normal"` |
| **`window.matchMedia`** | ❌ | **❌ 根本不存在** | `is not a function` → 媒体查询与 `prefers-color-scheme` 全废 |
| `prefers-color-scheme` | ❌ | **❌** | 同上，走 JS 挂 `.vt-dark` / `.vt-light` |

### ⚠️ 一处诚实的边界：「computed 有值」≠「确认渲染」

上表里标 ✅ 的项，**取证强度并不一样**，别混为一谈：

| 取证强度 | 项 | 含义 |
|---|---|---|
| **几何实测**（最强） | CSS 变量、`letter-spacing`、`transform`、布局测量 | 元素真的**动/变宽**了，是渲染结果 |
| **computed 有值**（较弱） | `outline`、`box-shadow`、`linear-gradient`、SVG 继承 | 只证明**属性被接受**。`box-shadow` 的历史行为是「需 `CSSNextSupport`，不开则静默忽略」——**computed 仍可能有值但屏幕上没有**，本探针无法区分 |

- 本机 `manifest.json` **完全没有 `featureFlags`**（即 `CSSNextSupport` 未开），
  而 `transform` 仍被几何实测证实生效 → 说明「`transform` 必须开 flag」这条旧说法在
  **PS 27.2 / UXP 9.0.2** 上不成立。**但不能反推 PS 2024 也成立。**
- **不开 flag 这个决定本身是对的、且不打算改**：色块 hover 反馈已由 `.sw-ring` 真实描边元素承担，
  工作正常；而 `CSSNextSupport` 自 **PS 26.0** 才有，与 `minVersion: 25.0.0` 冲突 ——
  **押它 = PS 2024 上退回无反馈。保持现状。**

### 这次修正**推翻了三条半旧结论**（都是量法错造成的假阴性）

1. 「CSS 变量不能用 / 读不到」→ 实际几何上完全生效
2. 「`letter-spacing` 不生效」→ 实际生效（**而 `index.html` 里本来就写着 `.06em` 字距，一直有效**）
3. 「`transform` 无效」→ 实际生效
4. 附带：「`offsetWidth` 恒为 0，绝不能用」也是假的 → 真机 **=100**，两套 API 都可用

**真正没被推翻的硬约束恰好是三条，也恰好是这批 UI bug 的根因**：
`flex gap` 不生效、SVG 不继承、`matchMedia` 不存在。

> **教训（已写进 `lib/cssprobe.js` 头部注释）**：
> 探针报「不支持」时，先怀疑**量法**，再怀疑特性。一个恒为 0 的读数，
> 更可能是「没量到」，而不是「真的没有」。**给几何探针配一个基座自证，成本极低。**

## 六、顺带修掉的一个真 bug（不在你报的 8 条里）

**点击「当前已经激活的颜色」会被判为失败**，面板弹「✗ 设前景色失败」。

真机日志：

```
palette set=foreground hex=#FFFFFF ... ok=false before=#FFFFFF readback=#FFFFFF
```

根因在 `lib/ps.js`：`ok` 被写成 `hit && changed`。
用户点一个本来就是当前前景色的色块 → `changed=false` → 判失败，
但**回读值和目标值明明一致**。

修：**`ok = hit`**，`changed` 只作为信息记录。

```js
// ⚠️ 旧版把 ok 写成 hit && changed，导致用户点一个当前已激活的色块时
// 被判为失败、面板弹出「✗ 设前景色失败」。
```

> 这是 `PROGRESS.md` 风险表里那条「**"设上了"的判据必须同时要求"值确实变了"**」的**过度应用**：
> 那条规则是说「测自检时，测试色不能碰巧等于当前色」，**不是**说「用户点同色也算失败」。
