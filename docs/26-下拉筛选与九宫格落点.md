## 一、需求 A：二层筛选 → 自绘下拉

### 做了什么

二层子组从"一排 chip"改成**下拉**：触发条显示「当前子类 + 计数 + ▾」，点开是浮层列表
（「全部子类」+ 各子组 + 计数）。一层（公司素材 / 我的收藏）仍是按钮 —— 与用户的设计一致。

### 为什么不复用现成控件（`docs/25` 已给证据，这里只留结论）

| 方案 | 为什么不用 |
|---|---|
| 原生 `<select>` | **外观改不动**，与"样式沿用现有风格"直接冲突；且设选中态只能走 `option.selected` |
| Spectrum `sp-picker` | 真机实测**未注册**（与伪造标签名的三项读数逐项相同） |
| **自绘** | 样式 100% 复用现有 token；风险已知且已有纪律 |

### 三条纪律（沿用调色板那次的四条）

1. **浮层不覆盖触发条** —— 纵向放在触发条下方 + 6px 间隙；
2. 关层由**容器根节点正着判**"这次点击还在不在这个组件内"，**不绑被覆盖元素的 `mouseout`**
   （子元素会成对触发，算错就是"关了又开"的振荡回路 —— 调色板悬停闪烁就是这么来的）；
3. 展开状态**幂等**（只切 class，不重建整行）。

### 🔴 新增一条**可测不变量**：浮层必须落在滚动容器之内

`.scroll` 有 `overflow-y:auto` ⇒ 浮层越界的部分**会被裁掉**，而用户只会看到
"下拉点开了但里面是空的" —— 这类错在真机上极难归因。所以 S20c 里把它变成硬判据：

```
浮层 24,161,110,214　滚动容器 0,34,420,647　完全在容器内=true
```

## 二、需求 B：九宫格落点

### 依据（`docs/25` §2.2 的实测）

`placeEvent` 的 `offset` 与图层位移 **1:1 精确**，所以"放到画布上的 (x,y)"就是一道算术：

```
offset = (x − 默认落点下素材左边缘, y − 默认落点下素材上边缘)
```

### 界面

详情区加了 3×3 的落点格子（左上→右下，居中在中间）+ 一行读数说明当前锚点会把左上角放到哪。
锚点选择**记在 `library-pref.json`** 里（与"上次看哪个库"同一个文件）。

### 校验方式：读回**真实图层 bounds**，与期望矩形**逐边比对**（容差 1px）

不是"命令没报错就算成功" —— 这条本项目栽过（`fill` 那次"不报错也不改像素"）。
S21 与 S25 都读 `readActiveLayerBounds()` 做这件事。

## 三、🔴 S24 探针的两个发现（其中一个改了设计）

### 发现 1：插件侧**能**建选区，而且和 ExtendScript **恰好相反**

S24 在同一台机器上试了四种写法：

```
DOM.select(2×2 数字)        ✗ 失败
DOM.select(扁平 4 数字)      ✗ 失败
DOM.selectAll()             ✗ 失败（saveDocumentSelection may modify…）
AM.setd(Chnl/fsel + Rctn)   ✅ 成功，建出 120,140,320,300
```

而 `docs/25` 记录的 **ExtendScript** 侧是：`selectAll` **行**、区域写法**全不行** ——
**两条 DOM 的可用性完全不能互相推断**。这正是当时坚持"结论不许迁移"的原因。

已把可用写法收进 `lib/ps.js setSelectionRect()`，注释里写明"这是真机试出来的"。

### 发现 2（**改了设计**）：默认落点 = "选区中心"，无选区则"画布中心"

```
无选区                 → 置入 bounds = 40, 80, 360, 320    （画布 400×400 居中）
有选区 120,140,320,300 → 置入 bounds = 60, 100, 380, 340    （选区中心 220,220 居中）
```

⇒ 统一规律：**默认落点 = 当前选区的中心；没有选区就是画布中心**（都不缩放）。

**连带后果**：我们的 `offset` 是**相对默认落点**的位移 ⇒ 有选区时它是叠在**选区中心**上的。
所以九宫格的基准**绝不能假设画布中心**，否则用户在有选区时选「左上」会整体偏掉。
⇒ 加了 `ps.placeBaseCenter()`，`anchorOffset()` 增加 `base` 参数。

### 附带事实：**这次置入会把选区吃掉**

S25 的读数直接写明了：`【置入后选区=无】`。
⇒ **"框哪儿放哪儿"是"每次插入前框一次"**。这条已写进界面提示，避免用户以为选区还在。

## 四、S25：把"offset 与选区默认落点叠加"钉成回归项

判据四步，每步读回真实 bounds 逐边比对：

| 步 | 条件 | 期望 | 真机 |
|---|---|---|---|
| ① | 无选区 · 左上 | (0, 0, w, h) | `offset=-40,-80 → 0,0` hit=true |
| ② | 建选区 R | `placeBaseCenter()` 报 `selection` 且中心 (220,220) | ✓ |
| ③ | 有选区 · 居中 | 素材仍**居中于画布**（40,80） | `offset=-20,-20 → 40,80` hit=true |
| ④ | 有选区 · 左上 | **(0, 0)** ← 只有 offset 叠在选区中心上才会是 0,0 | `offset=-60,-100 → 0,0` hit=true |

> **④ 的第一次运行是 FAIL 的**（落到了 −20,−20，即"画布中心 + offset"）。
> 当时 ③ 通过、④ 不通过，**任何单一规律都无法同时解释两步** ⇒ 说明两步之间有东西变了。
> 我没有改判据去迁就它，而是在探针里加了**选区存活读数** —— 一跑就看到 `【置入后选区=无】`，
> 于是给 ④ 补上"重建选区"这个**必要前置**，并把这件事当成一条事实记下来（见 §三 附带事实）。
> **教训同族**：读数分不清原因时，加一个能把原因区分开的读数，而不是猜。

## 五、⚠️ 一次**未复现**的失败（如实记录）

v0.3.0 的第二轮真机自检（`01:48:28`）出现过 **S20c FAIL**：

```
触发条出现=true·点开=true　浮层几何始终为 0（没进布局？）
子组选项「节日素材」=false → 卡片=-1
```

而**同一份代码**在它前一轮与之后**连续三轮**都是 PASS（浮层 `24,161,110,214`）。
当时那条读数**分不清**三种可能：没渲染 / 渲染了没展开 / 展开态被抹掉。
所以我没有猜，而是**补了两个能把原因区分开的读数**：

- `libBarSig()` —— 筛选区的**结构签名**（现在会打印
  `frow{chip:"",chip:"公司素材",chip:"我的收藏"} | frow.mid{wrap{open=false},trig,pop,opt:"",opt:"节日素材"}`）；
- `libPopInsideScroll()` 的失败分支 —— 同时报「**展开态现在是什么**」+ computed `display`，
  并明确区分"**状态还在、是没进布局**"与"**展开态没了**"。

**现状：加插桩后连跑三次均 PASS，该失败未复现。** 不宣称它已解决，也不宣称它不是问题 ——
**插桩已就位，下次出现会自己说清是哪一种**。
