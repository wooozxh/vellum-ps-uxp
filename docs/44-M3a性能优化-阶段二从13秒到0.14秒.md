# 44 · M3a 性能优化：把阶段二从 13.5s 压到 0.14s（v0.4.7）

> 用户选择「先做性能优化」。目标：每次生成表格的 **16 秒**（其中阶段二 13.5s）压下来。

**真机 50/51 连跑三轮**（`22:45:29` / `22:47:28` / `22:50:41`，`dur≈64–65s`，唯一 FAIL = 已知 S17）；**离线 66/66**；ccx 0.4.7。

---

## 一、第一步：**先分段量，别猜**

给阶段二加分段计时（选择 / 改名 / 对齐 + 四分位），真机读数：

| 场景 | 选择 `doc.activeLayers=` | 改名 `layer.name=` | 对齐 `batchPlay(set …)` |
|---|---|---|---|
| 2 格 / 3 层 | 21ms（11ms/格） | 31ms（16ms/格） | 45ms（**23ms/格**） |
| 12 格 / 23 层 | 155ms（13ms/格） | 184ms（15ms/格） | 220ms（**18ms/格**） |
| **35 格 / 51 层** | **6845ms（196ms/格）** | **5920ms（169ms/格）** | 815ms（**23ms/格**） |

三条结论（都是读数，不是推理）：

1. **`batchPlay` 不是瓶颈** —— 它对格数**线性**、23ms/格，而且**便宜**。
   （我原本的假设是"AM 往返太贵、要靠 `_id` 合批对齐"—— 实测**假设错了**。）
2. **两个 UXP DOM 写操作才是**：层数从 3 → 51（×17），单次代价从 11ms → 196ms（**×18**）
   ⇒ **O(格数 × 文档层数)**。
3. **不是 O(n²) in 格序**：四分位 选择 `2195/1625/1636/1389`、改名 `1436/1523/1680/1281`
   —— 前 1/4 最慢、后 1/4 最便宜，说明涨的是"**文档多大**"而不是"第几格"。

⇒ 结论：**开销在 UXP DOM，不在 AM。** 那正确的优化不是"把 AM 合批"，而是**让这两个 DOM 写操作彻底消失**。

---

## 二、第二步：隔离验"能省掉阶段二"的加法（各一条命令，发完立刻读回）

按项目纪律（v0.4.0 卡死宿主的正是"推理出来的描述符被合批发出去"）：**一条命令单独发、发完读回、两条分开验**。

| 试的加法 | 命令有没有报错 | **读回** | 结论 |
|---|---|---|---|
| `name` 放进 `make textLayer` | 没报错 | 层名 = **"甲"**（= 文字内容） | ✗ **被忽略** |
| `paragraphStyleRange` 放进 `make textLayer` | 没报错 | 对齐 = **alignmentType:center** ✓ | ✅ **生效** |
| AM：`set` + `_target:[{_ref:"layer",_id:N}]` + `to:{name}` | 没报错 | 层名 = `vt-s46-byid` ✓ | ✅ **生效** |
| `name` 放进 `make contentLayer`（矩形） | 没报错 | 层名 = **"矩形 1"** | ✗ **被忽略** |

（S45 / S46 两条探针，日志里各自留了"即将发第 N 条"的分野线；四条都没触发模态框。）

**两个"没报错但不生效"的读数很值钱**：只写"命令没报错"会把它们当成能力 —— 这里全靠**读回**才分开。

---

## 三、第三步：改成新设计（阶段二 = 一次 batchPlay）

```
① 建层（一次 batchPlay，命令数不变）
   · 文字层**内联**段落对齐（S45 已验证）
   · 不再传 `name`（反正被忽略）

② 命名（**一次** batchPlay）
   · 先**只读**遍历一次组里的图层拿 id（便宜）
   · 建层顺序 = [背景 → 线 → 文字]，PS 每建一层都放在组内最上面 ⇒ 组内数组的**逆序**就是建层顺序
   · 按 `_id` 发 50 条 `set {name}`（S46 已验证）
   · **层序对不上就不改名**（宁可不命名，也不能把名字安到错层上）
```

- `alignMode:"dom"` / `nameMode:"dom"` 保留为**退回路径**（可跑、可对照）。
- 产物：**批次数从 37+ 降到 2**；UXP DOM 的**写**操作全部消失。

## 四、结果

| 指标 | 优化前 | 优化后（三次真机） |
|---|---|---|
| 51 层 / 35 格 **总耗时** | 16086ms | **3395 / 3482 / 3960ms** |
| 阶段二 | 13455ms | **133 / 138 / 1418ms**（改名批次稳定 **105–116ms**） |
| batchPlay 批次数 | 37+ | **2** |
| S40（23 层 / 12 格） | 阶段二逐格 DOM | 阶段二 = **am**，改名 **22/22**，批次 **60–68ms** |

⇒ **4.1–4.7× 提速**（真机上"用时"从 16s 变成 3.4–4.0s）。

**顺带的一个 UX 改善**：命名现在是"所有图层一起改"，所以形状层也有名字了 ——
`背景 · 表头` / `线 · 横 3` / `外框 · 上` / `文字 R2C3 价 199`（以前形状层叫"矩形 1..14"）。
**S40 新增断言**验证"外框 · 上"真的存在（`make contentLayer` 的 name 被忽略，所以必须验"事后 set 生效了"）。

## 五、离线断言（发出去之前先把命令形状钉死）

`tools/offline-smoke.cjs` 的 M3 段按新设计重写（**离线 65 → 66**）：

- ② 文字命令**该带**已验形状的 `paragraphStyleRange`：只许 4 个键（`from/to/paragraphStyle/align`），
  枚举族必须是 `alignmentType`、值必须是 left|center|right；**不许带 `name`**。
- ④ 落地形状：**批次数 = 2**、改名条数 = 层数 − 1、**全按 `_id`**、**id 顺序 = 建层顺序**、
  名字首/中/末对（`背景 · 表头` / 第一格 / 最后一格）、**0 条逐格对齐**。
  > id 顺序这条最要紧：反了就是整张表的名字安到别的层上，真机上极难查（现在没有"逐格 DOM 改名"兜底了）。
- ⑤⑥ 两条**负对照**：文字判据只放过 5 条构造命令里的 **1** 条（带 name / 多键 / 错枚举族 / 错值都得抓住）；
  改名判据只放过 3 条里的 **1** 条（"按名字选层"这种**没验过**的形状必须被拒）。

## 六、教训（已写进 MEMORY）

1. 🔴 **UXP DOM 的写操作单次代价随"文档层数"增长**（`activeLayers=` 11→196ms、`layer.name=` 15→169ms）
   ⇒ **绝不放进"按格/按项循环"**；能挪到 AM 就挪（AM 线性、还能合批）。
   只读遍历便宜（拿 50 个 id 只花一次遍历）。
2. 🔴 **"命令没报错" ≠ "字段生效"**：这一轮 4 条被试的加法里，**2 条是"静默无效"**
   （`name` 在 `make textLayer` 与 `make contentLayer` 里都被忽略）。判据必须**读回目标状态**。
3. 🔴 **先分段量、再决定优化什么**：我原本以为热点是 `batchPlay`（要去做 `_id` 合批），
   实测它恰恰是三者里最**便宜**的 —— 如果按假设动手，会白干一轮还不解决问题。
4. 探针的判据要**只押"要依赖的那一条"**：S45/S46 初版把"两个加法都成立"当判据 ⇒ 探针 FAIL，
   但那是**读数**（一个成立一个不成立），不是产品坏。改成只押依赖项，把另一条写进读数。
