## 二、发现的真 bug：`mtM` 类覆盖 —— 位移耗时**恒为 0（假读数）**

`lib/ps.js` `exportByRows()` 里：

```js
let tWrite = 0;
let tMove  = 0;              // ← 声明后**从未被赋值**
...
out.moveMs = Date.now() - t3;   // ← 真实位移耗时量在这里（逐份"选中→translate"）
...
out.writesMs = tWrite;
out.moveMs  = tMove;            // 🔴 一行把它覆盖回 0
```

⇒ 真机日志里那句「**移动 0**」是假的。真实位移耗时被藏在「总耗时 − dup − step2」里：

| 那一次      | 总      | dup  | step2 | 剩下的（≈位移 + 模态开销）          |
| -------- | ------ | ---- | ----- | ------------------------ |
| 00:22:36 | 1308ms | 32ms | 809ms | **467ms / 6 份 ≈ 78ms/份** |

**为什么这条重要**：待办池 #2 是「N=20+ 的规模与性能」，而**位移那一段是瞎子**。  
V0.4.7 的教训是「先分段量再优化」—— 这里连量都量不到。

同族还有一条：`step2Ms` 的定义**不含位移**（`out.step2Ms = Date.now() - t1` 在位移循环之前算），  
日志里把「写 / 移动」并排挂在 `step2=` 后面会让人以为加起来等于 step2。**「反馈正确」也算正确性的一部分。**

## 六、方法学（本轮新增/复述）

- **「读数是 0」也可能是个 bug，不是"很快"** —— 发现它靠的是「总耗时 − 各分项 ≠ 0」这个恒等式。  
  **给分段计时加一条自洽检查式（分项之和 ≤ 总）比多加一个计时器更有用。**
- **同名/同类变量对写**：`tWrite/tMove` 两个长得一样的累加器，一个被赋值、一个没有 ⇒ 后者静默覆盖前者。  
  与 `docs/42` 的「看起来一样的两处别用字符串替换改」是**同族**（这次是"看起来一样的两处别搞混")。
- **观测也是产品的一部分**：`step2Ms` 不含位移却把位移并排写在括号里 —— **判据正确 ≠ 反馈正确**。
