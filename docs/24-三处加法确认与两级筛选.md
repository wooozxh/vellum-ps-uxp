> 会话：2026-10-10（第 17 次，跨零点）
> 触发：软件侧按契约 §十「加法」流程提了 **3 处加法**，请插件侧确认

## 二、插件侧的处置（三个不同的答案，各有理由）

### ③ `parentId` → **必须实现**

因为**不做两级不是"少个功能"，而是"错的 UI"**：筛选行是按分组名平铺生成的，
一旦数据里出现 `parentId`，**父组和子组会变成同级 chip** —— 父组点下去可能一张素材都没有，
而它的子组却和它并列摆在旁边。用户看到的层级是假的。

实现（`lib/mirror.js`）：

- 展平时解析成 **`group`（顶层名）/ `sub`（子组名）** 两个字段；顶层条目的 `sub` 为空串。
- 按 `sortOrder` 排序，且**父组在前、它的子组紧随其后**（否则网格顺序是乱的）。
- 容错一律"**宁可当顶层，也绝不丢素材**"：
  `parentId` 缺失 / `null` / 空串 → 顶层；**指向不存在的分组** → 顶层；
  **三层以上 / 成环** → 由结尾的兜底循环按顶层吐出。
  （丢素材是界面完全不报的那种错，所以这里宁可难看也不能少。）
- 新增 `groupTree(items)` 给 UI 与自检复用，`count` **含子组** ——
  这样"点父组后网格里的卡片数"才对得上 chip 上的数字。

界面（`tools/library.js`）：筛选区第二行，**子组 chip 缩进 + 小一号**；
且**只在当前父组真有子组时**才出现。

### ② `source` → **实现，但只在"能起区分作用"时出现**

写在纸面上是"加个字段"，落到界面上是一个判断：**这一行值不值得画**。

- 「来源」筛选行**仅在当前分组内真有 ≥2 种来源时**出现 —— 只有一种取值时，
  那一行永远只有一个可选项，那是噪音（沿用本项目一贯的"不构成筛选就不画"）。
- 卡片角标同一套规则（两种来源混排时才给每张卡挂「公司」/「我的」）。
- **详情行始终显示来源**（那里不占额外空间，也不构成噪音）。

> 这里有个容易写错的细节：来源行的取值必须基于「**只按分组筛过**」的集合来算，
> 不能基于"最终可见"的集合 —— 否则一点「我的」，可见集合里就只剩一种来源，那一行自己消失了。

### ① 命名空间 → **对插件零改动，但价值最大**

`asset.thumb` 对插件**一直是"镜像内不透明路径"**（`lib/mirror.js` 按字符串取图、
`parts = String(asset.thumb).split("/")`、**从不解析文件名**），所以加前缀不破坏任何东西。

**但它让一个潜伏的缺陷暴露了出来** —— 见下节。

## 三、🔴 本轮最有价值的发现：缩略图缓存键跨库冲突

### 症状

`lib/mirror.js` 的缩略图缓存原来是：

```js
const key = String(asset.id);   // ← 问题在这
if (thumbCache.has(key)) return { ok: true, url: thumbCache.get(key), cached: true };
```

**两库的 `asset.id` 各自从 1 起** ⇒ 两库的 #1 是**同一个键**。

### 为什么"revision 变了就清缓存"兜不住

原设计里唯一的保护是 `clearThumbs()`：

```js
if (revision !== undefined && revision !== cachedRev) { clearThumbs(); cachedRev = revision; }
```

可**两个库的 revision 完全可能相等**。最典型的一种：

> **首次同步之后，`task rev=1`、`brand rev=1`。**

这时从任务库切到通用库：`revision === cachedRev` ⇒ **不清缓存** ⇒
通用库的 #1 命中任务库 #1 的缓存项 ⇒ **网格里显示的是上一个库的缩略图**。
**不报错、不空白，只是图不对** —— 最难发现的那一类。

### 修法

键改成 **`asset.thumb`**（`thumb/t401.png` / `thumb/b1.png`）—— 它**自带命名空间**，
天然唯一。`clearThumbs()` 保留（换 revision 时释放旧 objectURL，防泄漏）。

离线断言 **32** 用"**同 id、同 revision**、只差 thumb"的两个 asset 把这条钉死：

```
task   id=1 ok=true（cached=false）　brand id=1 ok=true（cached=false）
两条 URL 不同=true（键若仍是 asset.id 则必然相同）　同 thumb 二次命中缓存=true
```

> ⚠️ **诚实标注**：这条缺陷是**读代码 + 离线断言**确认的，
> **没有在真机上复现**（复现需要两库 revision 恰好相等，而桩里 task rev=87 / brand rev=3）。

## 四、顺带修掉自检自身的一处竞态（同一族缺陷的第二次）

### 现象：**同一份代码，连跑两次结果不同**

```
00:22 第 1 次：S20c PASS  S20d PASS   → 25/26
00:24 第 2 次：S20c FAIL  S20d FAIL   → 23/26   ← 代码一个字没改
```

### 归因

`tools/library.js` 的 `switchScope()` 是**异步的**（里面有 `await loadScope`），
而 S20b 结尾"切回原库"的那次点击**没有被等待**：

```js
const back = document.getElementById("vt-lib-tab-" + activeId);
if (back) syntheticClick(back, false);   // ← switchScope 还在飞
```

紧接着 S20c 就去操作**筛选行**，而它等的条件是「tab 高亮 + 网格里有卡片」——
**这两条都会被上一个库留下的旧网格满足**。于是量到的筛选行属于**旧库**：

- 第 1 次碰巧过关：旧网格属于**通用库**，而操作目标也正是通用库 → 顺手通过；
- 第 2 次显形：旧网格属于**任务库**（只有 1 个分组 ⇒ **不画 chip**，只显示"共 2 张"）
  → `libChip("公司素材") = null`、`libChip("user") = null` → 两条 FAIL。

> **这是同一族缺陷的第二次。** v0.2.7 的 S20b 也是这个毛病：
> 判据描述的是"**DOM 里现在有什么**"，而不是"**我要的那个库渲染完了没有**"。
> 教训一句话：**判据要描述"我等的那个东西"，不是"看起来像的东西"。**

### 修法

让**网格自带身份**（`tools/library.js renderGrid`）：

```js
"data-scope": String(S.tabId || ""),
"data-rev":   String(S.revision == null ? "" : S.revision),
```

自检的等待条件**点名是哪个库**（`libSwitchTo` / `libWaitCards` / S20 的缩略图等待 / S20b）。

### 同时确立一条做法

**改完自检要连跑两次，而且两次的起始状态要不同。**
这一条缺陷就是"两次结果不一样"才被抓出来的 —— 跑一次的话它会一直"偶然通过"。
