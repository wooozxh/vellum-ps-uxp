# 12 · 多版本兼容性策略（PS 2024 / 2025 / 2026）

> **状态**：**已定稿**（2026-10-10 用户拍板）—— 兼容性作为**横切约束并入 M1**，不单开里程碑。
> **起因**：用户提出 —— 本机是 PS 2026，但同事有 2024 / 2025，插件是否需要考虑兼容性。
> **结论（先说）**：**需要考虑，而且是"现在最便宜"的时刻。** 目前一行业务代码都没写，兼容性是**设计约束**（近乎零成本）；等 M1–M3 写完再补，就是**返工**。

---

## 一、事实（已核实，非推测）

### 1.1 版本映射：PS 大版本 ↔ UXP 运行时

来源：Adobe 官方 `developer.adobe.com/uxp/uxp-api/versions` 与 `ps_reference/changelog`。
**⚠️ 官方表格在抓取时有错位风险 → 最终以"插件自报的 UXP 版本"为准（见 §四 D 的体检方案）。**

| PS 大版本 | 内部版本号 | 随附 UXP | 备注 |
|---|---|---|---|
| Photoshop 2022 | 23.x | UXP 5.5 – 6.2 | 不在支持范围 |
| Photoshop 2023 | 24.x | UXP 6.3 – 7.1 | 不在支持范围 |
| **Photoshop 2024** | **25.x** | **UXP 7.2 – 7.4+** | 最老的一档，**风险主要在这** |
| **Photoshop 2025** | **26.x** | **UXP 8.0 – 9.x** | 后期小版本已升至 UXP 9 |
| **Photoshop 2026** | **27.x** | **UXP 9.0.2 – 9.3+** | 本机实测 27.2 = **UXP 9.0.2** |

**关键判断**：真正的兼容分界线是 **UXP 7.x ↔ UXP 8/9.x**，而不是"PS 年份"。
PS 2025 与 2026 的 UXP 版本可能**很接近**（都是 9.x），差异主要在 PS 2024。

> **一个反直觉点**：由于小版本更新节奏不同，**不能假设"PS 2026 的 UXP 一定比 PS 2025 新"**。
> 官方表显示 26.11 → UXP 9.2.0，而本机 27.2 → UXP 9.0.2。→ 再次说明：**以自报版本为准，别用年份推断能力**。

### 1.2 本项目已经踩到过真实的版本行为差异（活样本）

`docs/04` 记录的实测结论，**本身就是一条版本差异证据**：

| 事实 | 在本机（PS 2026 / UXP 9.0.2） |
|---|---|
| `batchPlay` 的 `make` + `textKey` 建文本图层 | ❌ **只建出普通层**（图层名却是对的 → 极易假阳性） |
| DOM `app.activeDocument.createTextLayer({contents})` | ✅ 可行 |

**反向推论（重要）**：PS 2024 / 2025 很可能**仍然吃 `batchPlay` 那条老路**（我们没测过，但这是老 API）。
→ 所以正确做法**不是"选一条路"**，而是**两条路都留 + 运行时探测**（见 §四 B）。

**结论：版本行为差异不是理论风险 —— 它已经发生过一次了。**

### 1.3 `manifest v5` 的门槛

- 官方样例中 `manifestVersion: 5` 的最低 `minVersion` 见 `23.0.0`；Spectrum Web Components 的 starter 用 `24.4.0`。
- → **manifest v5 在 PS 24.4（UXP 7.0）起已稳定可用**，PS 2024 及以上**不存在 manifest 版本障碍**。
- 本项目 `hello-world` / `link-probe` 现声明 `"minVersion": "23.3.0"` —— 这是**从样例抄来的，从未验证过**，本次一并修正。

### 1.4 🔴 连锁影响：PluginData 路径**含 PS 主版本号**（此前未被注意到）

镜像目录是：

```
%APPDATA%\Adobe\UXP\PluginsStorage\PHSP\<PS主版本号>\Developer\<插件id>\PluginData\
```

| 机器上的 PS | 实际路径 |
|---|---|
| PS 2026 | `...\PHSP\27\...`（本机实测） |
| PS 2025 | `...\PHSP\26\...` |
| PS 2024 | `...\PHSP\25\...` |

**对联动契约的影响（两条，都需记入 `LINK-LOG`）**：

1. **同一个人若同时装了 2025 与 2026** → 会出现**两个** `PluginData\library\` 目录，软件侧"动态发现"的算法需明确**写哪一个**（建议：全部命中都写，或写"用户指定"的那一个）。→ **契约 §七 的发现算法需要补一条**。
2. **缓存/镜像不跨版本共享** → 每个 PS 版本各存一份镜像。对体积无碍（§10.6 已实测：3000 素材 ≈ 23 MB），但要**明确这是预期行为**，免得同事误以为"数据没同步过来"。

> `docs/04` 与契约 §九 都记过"路径含 PS 版本号"，但**从未把它和"多版本共存"这个场景联系起来**。这次补上。

### 1.5 分发方式（后续里程碑，但受本次决策影响）

UXP 插件正式分发 = **`.ccx` 包**（由 UXP Developer Tool 打包），目前项目还在"开发者模式加载"阶段。
`minVersion` 的值**直接决定同事能不能装上** —— 所以这条不只是技术问题，也是**部署问题**。

## 二、真正要防的两类风险

| 风险 | 例子 | 后果 |
|---|---|---|
| **A. 硬门槛**（版本不够 → 直接装不上/报错） | 用了某版本才有的 API | 同事**整个插件打不开** |
| **B. 静默行为差异**（能跑但结果不对） | 文本图层建成了普通层 | **更危险** —— 表面成功，实际错误（本项目已踩过） |

**B 类比 A 类更可怕**，因为它不会报错。→ 所以策略的重心是**探测 + 断言**，而不是"版本号比较"。

## 四、策略（五条）

### A. `minVersion` 定到 **25.0.0**（= PS 2024 起）

- 语义清晰：**"PS 2024 及以上可用"**，与用户的实际团队情况一致。
- **不要为了"兼容更多"把 minVersion 往下压** —— 压低了只会让更老的 PS **装上但跑错**，比装不上更糟。**宁可装不上（有明确报错），也不要静默出错。**
- **已定（2026-10-10）**：`minVersion: "25.0.0"`（PS 2024 起）。
  ⚠️ 这是**暂定值** —— 同事中是否有 PS 2023 或更老**尚未调查**，用户将尽快在公司确认；届时若确有其事，门槛需重算。

### B. API 白名单 + 逐项标注"最低可用版本"

新建并维护一张表（放在本文档 §五，随开发逐行填）：

| API / 能力 | 最早可用 PS 版本 | 是否已实测 | 用在哪 |
|---|---|---|---|
| `executeAsModal` | 22.0 | ⬜ | 全局 |
| `batchPlay`（基础） | 22.0 | ⬜ | 全局 |
| DOM `createTextLayer` | 待查 | ✅ 仅 2026 | 文本/表格 |
| `batchPlay` `make`+`textKey` | 老 API，2026 起失效 | ✅ 仅 2026 | 退役路线 |
| `storage.localFileSystem` | 待查 | ⬜ | 数据存储 |
| `<input type="color">` | **待实测（重点）** | ⬜ | **M1 调色板** |
| `sp-*` 内置组件各控件 | 待查 | ⬜ | 全局 UI |

**纪律**：每用一个新 API，**先查官方文档的 "since" 标注**再写。查不到就列入"待实测"，不硬上。

### C. 能力探测 + 双路降级（针对已知差异）

对已知有版本差异的能力，**不写死一条路**：

```js
// 示意：先试新路，失败走老路，并把走了哪条路写进 boot.log
async function createTextLayerCompat(doc, text) {
  try {
    return await doc.createTextLayer({ contents: text });   // 新路（DOM）
  } catch (e) {
    log("DOM 建文本层失败，回退 batchPlay", e.message);
    return await legacyTextLayerViaBatchPlay(doc, text);    // 老路
  }
}
```

**判定必须用"名字 + 类型"双条件**（沿用 `docs/04` 的教训）—— 只看名字会假阳性。

### D. 一键环境体检（**这是本次最有价值的产出**）

做一个 `env-check` 面板插件（复用 `hello-uxp` 的成熟思路），同事装上后点一下，输出：

- PS 版本、**UXP 版本**（`require('uxp').versions.uxp`）、平台
- 上表每一项 API 的**实际探测结果**（可用 / 不可用 / 行为异常）
- 结果写入 `boot.log` + `report.json`，**同事把文件发回来即可**

**为什么这是关键**：本机只有 PS 2026，**2024/2025 的真实行为我无法在本机验证**。体检插件把"我猜"变成"数据"。

### E. 镜像是"按 PS 版本各存一份"，这是预期行为

见 §1.4。不做跨版本共享 —— 简单、无坑。但要在插件 UI 或文档里说清，避免误解。

## 六、限制与诚实说明（**请你知悉**）

1. **本机只有 PS 2026，2024 / 2025 的结论我无法在本机实测。** 需借同事机器跑一次 §四 D 的体检插件 —— 这属于"物理上没法代劳"的部分，需要你协调。
2. §1.1 的官方版本表**存在抓取错位风险**，故策略里**不依赖它做运行时判断**，只用于制定 `minVersion` 和排优先级。
3. 本文档是**策略**，不是"把每个 API 的版本都查完了"。**逐项版本查证会随 M1 开发同步进行**（每用一个查一个，记入 §五 的表）。

## 七、对 M1 的影响（结论）

**M1 不受阻塞，但有两个动作要并进去：**

1. **M1 开工第一件事**：跑一个 **UXP 能力体检探针**（在真机验证"设前景/背景色"的同时，把 §五 表里 M1 会用到的项一并探掉）。
2. **M1 代码里所有"有版本门槛"的能力，一律走探测降级**（§四 C），**不裸调**。

> 也就是说：**兼容性不额外开一个里程碑，而是作为"横切约束"并入 M1。**

## 九、`env-check` 体检插件（本轮产出）

**用途**：在**无法开发**的机器（同事的 2024 / 2025）上，一键采集真实的 UXP 版本与 API 行为，把"我猜"变成"数据"。

**它测什么**（每一项都带超时与原始错误捕获，**绝不卡死模态**）：

| 组 | 项 |
|---|---|
| A 环境 | PS 版本（DOM / batchPlay / uxp.host 三路交叉）、**UXP 版本**、宿主名、平台、插件目录、数据目录 |
| B 核心 API | `executeAsModal`、`batchPlay`（只读 get）、`storage.localFileSystem` |
| C 版本差异项（**重点**） | DOM `createTextLayer`（在临时文档上）、`batchPlay` `make`+`textKey` 建文本层（**只判类型，不做后续 set**，避免 `docs/04` 的原生框卡死） |
| D M1 地基 | **设前景色 / 背景色**（设→回读比对→恢复原值）、`<input type="color">` 支持与否 |
| E UI 组件 | `sp-button` / `sp-textfield` / `sp-picker` / `sp-slider` 等内置组件的实际可用性 |

**输出**：`report.json`（结构化，脚本可读）+ `boot.log`（流水）+ **面板直接显示全文**（同事截图即可回传）+ **「另存报告」按钮**（`getFileForSaving`，存到桌面再传回）。

**分发**：用 `uxp plugin package` 打成 **`.ccx`**（官方说明：`.ccx` **不需要包级签名**，双击 → Creative Cloud 安装）。离线/受限环境可解压 `.ccx` 直接拷入 PS 的 `Plug-ins` 目录。

**为什么归在"物理上没法代劳"**：本机只有 PS 2026，2024/2025 的真实行为**不可能在本机复现** —— 必须由你协调同事机器。

### 9.1 本机基线（PS 2026 / UXP 9.0.2，已实跑）

**17 / 21**，4 个 FAIL 全部**合理且预期**（不是缺陷）：

| FAIL 项 | 含义 / 对策 |
|---|---|
| `photoshop.app.version`（DOM） | 本版本读不到 → **改用 `uxp.host.version`** |
| `batchPlay` 读 `application.version` | 读不到；官方返回的 `_warning` 明确"请改用 `require('uxp').host.version`" |
| `batchPlay make+textKey`（老路） | **预期 FAIL** —— 2026 上只建普通层（`kind=pixel` / `layerKind=1`）→ 走 DOM |
| `<input type="color">` | `type` 保留 `"color"` 但 `value=null` → **实现不完整，M1 不应依赖它** |

**M1 调色板地基（本机已实测通过）** —— 完整写法与两个坑见 `DECISIONS.md` 与 `env-check/README.md` §六。要点：
**GET 与 SET 的 `_target` 写法不对称**（`[prop, appRef]` 能读不能设；设色须 `[ref:color]`），
且**命中判据必须要求"值确实变了"**（否则测试色恰好等于当前色时会假阳性）。

### 9.2 分发（已打通）

`uxp plugin package` → `dist/com.wooozxh.envcheck_PS.ccx`。**`.ccx` 不需签名**；
有 CC 桌面端则**双击安装**，受限环境可**解压拷进 PS 的 `Plug-ins` 目录**。
打包硬要求：manifest 必须声明 `icons`（否则打包失败）—— 图标已用纯标准库 Python 生成。
