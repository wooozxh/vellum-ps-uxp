## 一、第 1 条：步进器 —— 根因不是"压缩"，是**容器不肯画大**

### 证据（字符画，不是猜）

用户给了一张 190×105 的截图。我把它按像素扫成字符画（`#`=亮 `+`=中 `.`=线 `o`=sink ` `=面板底）：

```
字号   [边框 112..143]   12 落在 152..162   + 落在 188..193
      框内：− 在 121..127（正中 ≈124 = 112+1+22/2 ✔）
      ⇒ **子元素位置是对的**（22/42/22 各自到位），只有**边框盒画了 32px**
```

也就是说：`−` 归位、`12` 归位、`+` 归位，**唯一错的是容器自己的边框盒大小**。
用户看到"边框只包住 −，数字和 + 掉在框外"，第一反应是"减号的容器过宽"——描述不同，同一个东西。

### 根因

**UXP 计算 flex 容器的自身尺寸时，按子元素的"内容宽"求和，不认 `flex-basis`。**

- 子元素 `flex: 0 0 22px / 42px / 22px` —— **有效**（位置都对）；
- 容器 `.tnum`（`display:flex`，无显式宽）—— 被算成 `−`(8) + `12`(15) + `+`(8) ≈ **31px**。

v0.4.4 我给容器加的 `flex: 0 0 auto` 只能管"**别被压缩**"，管不了"**我该画多宽**" —— 所以那一版没修好，这次的观感只是从"灰字压数字"变成"数字掉在框外"。

### 修法

```css
.tnum { width: 88px; box-sizing: border-box; }   /* 88 = 1 + 22 + 42 + 22 + 1 */
.tnum.cpt { width: 64px; }                        /* 64 = 1 + 16 + 30 + 16 + 1 */
```

并把内边距那一行的 4 个改用**紧凑版**（`cpt`）—— 4 × 88 = 352 > `.ct` 可用的 ~308px，
必然溢出；4 × 64 + 3 × 5 = 271 ≤ 308 ✔。

📌 **纪律**（写进 MEMORY）：**UXP 里凡是靠 flex 容器"自己算"尺寸的地方，都要给显式 width/height。**

### 验证（真机 S44，两道）

| 读数 | 结果 |
|---|---|
| 字号步进器 / 行高步进器 边框盒宽 | **88 × 24** ✓（原 32） |
| 子格宽度 | **[22, 42, 22]** ✓ |
| 子元素是否都在盒内 | **true** ✓ |
| 内边距 4 个宽 | **[64, 64, 64, 64]** ✓ |
| 4 个是否重叠 | **不重叠** ✓（最后一个右边界 381 ≤ 面板右 420） |

截图存证：`docs/shots/v0.4.5-修复前-边框只包住减号.png` → `v0.4.6-修复后的步进器.png`。

## 二、第 2 条：垂直对齐 —— **其实生效了，只是既看不出来、又整体偏高**

### 先把用户那张表量出来（不猜）

用户画布上那张 `表格 · prices-2026`（行高 28 / 字号 12，选的是**底对齐**），
我按 200% 缩放逐像素量墨迹：

| 行 | 行 canvas 区间 | 墨迹中心 | 相对行中心 |
|---|---|---|---|
| 表头 | 0–30.5 | 11.75 | **−3.50** |
| 数据行 1–6 | 每行 28 | 逐行一致 | **−1.50** |

对照三种对齐的**理论值**（当时实现：箱高 1.32em，按"框"对齐）：
顶 −5.1 / 中 −3.0 / 底 −0.9 ⇒ 数据行的 −1.5 **正好是"底对齐"** ⇒ **功能是生效的**。

### 但有两个真问题

1. **可调空间太小**：行高 28 − 上下内边距 8 = 内容高 20，而箱高 1.32 × 12 = **15.84**
   ⇒ 三档总共只能挪 **4.16px**（每档 2px）。肉眼看不出差别，用户说"没生效"完全合理。
2. **整体偏高 ≈3px**：PS 的框文本把第一行 baseline 放在 `box_top + ascent` 处，
   **字形贴着箱顶往下画** ⇒ 我们按"框"居中，字就永远看着偏上。

### 修法（两条，都在 `lib/table.js`）

```
① 箱高 1.32em → **1em**（箱高不影响文字位置 —— S43 实测过 —— 却直接吃掉可调空间）
   位移 4.16px → **10.16px**（用户这套配置，2.4 倍）
② 对齐基准从"造"改"字"：按**墨迹**对齐
   INK_MID = 0.40em（墨迹中心相对箱顶）　INK_BOT = 0.82em（墨迹底边）
   · 垂直居中 → 墨迹中心 = 行中心
   · 底对齐   → 墨迹底边贴下内边距线
   · 顶对齐   → 框顶贴内边距线
```

常数来自**真机实测**（不是推导）：12px 汉字 0.39em / 12px 数字 0.385em / 18px 汉字 0.43em
⇒ 取 0.40em，残差 <0.6px。

### 还顺手把"为什么看不出差别"写在界面上

样式 →「表头」/「行」tab 的垂直对齐下面多了一条**动态**说明：

> 三档之间的文字位移约 **10.2px**（由行高 28 与字号 12 决定）。行高比字号大得越多，差别越明显。

（值变了就地刷新，不重建面板；行高/字号/内边距任一改动都会更新它。）

### 验证（真机 S43，两组样式 × 三档）

| 组 | 档 | 墨迹中心（实测 / 期望） | 差 |
|---|---|---|---|
| 60/18 | top / middle / bottom | 71/71.2 · 180/180 · 289/288.4 | ≤0.6px |
| **28/12（用户实配）** | top / middle / bottom | 339/338.8 · 434/434 · 529/529 | ≤0.2px |

- 位移：宽松组 **218px**（期望 217.2）、实配组 **190px**（期望 190.2）—— 含三张表纵向错开的 180px，
  即**单格内位移 10.16px** ✔
- **居中档落点 vs 行中心 = 0px** ✔（用户要的那件事）

## 三、这一轮我自己的三个错（都记下来，因为都是"判据/探针"的错）

1. **S43 的行中心忘了加 `k × 90`**：三档是三张表，纵向各错开 90px。
   我拿"第一张表的行中心"去比"第二张表的墨迹" ⇒ 报 90px 偏差，把一个**全对**的产品判成 FAIL。
   ⇒ **判据里的"分母"必须是同一张表的同一行。**
2. **S44 等错了东西**：点 tab 会 `dom.clear(g.gb)` 重建整个 pane，`#vt-tbl-fs` 是**刚被创建**的；
   我只等了"元素存在"就去量几何 ⇒ `0×0`。
   **UXP 的布局是异步的**（这条项目里早就有）⇒ 要等**布局落定**（宽高非零），不是等元素出现。
   （同一轮里 g1 的行高是几秒前建的，所以量到了 88 —— 这个对比正好把原因钉死。）
3. **`inside()` 对全 0 恒真**：`k.l >= box.l - 1 && k.r <= box.r + 1` 在**全 0** 时必然成立
   ⇒ "都没量到"被判成"都在盒内"。修法：先要求盒与子元素**宽度非零**。
