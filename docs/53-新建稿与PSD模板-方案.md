## 三、JSON 规范建稿

### 3.1 它是怎么工作的

不打开任何文件，让 PS 按一段「说明书」**当场造**出一张新稿。
平时在「新建文档」对话框里手填的值（尺寸 / 分辨率 / 色彩 / 出血），改成从 JSON 读 ——
值不再靠人记、靠人手打。

好处三条：**规范从第一秒就对**（不会"忘了改分辨率""开了 RGB 才想起要印刷"）；
**参考线随建稿写入**（顺带堵上体检里「出血 无法判断」那个洞 —— 线是我们自己画的）；
**可下发**（一段 JSON = 一份规范，将来由软件侧推给全部门）。

### 3.2 规范文件分两层（`spec.json`）

```jsonc
{
  "meta": {                       // ← 插件自己用，**绝不传给 PS**
    "specName": "Vellum 出图规范",
    "specVersion": 3,
    "effectiveFrom": "2026-10-12",
    "usage": "print",             // print | screen | social ⇒ 决定套哪套检查规则
    "bleedMm": 3,                 // 出血（写参考线用）
    "safeAreaMm": 5,              // 安全区
    "layerStructure": ["背景", "主视觉", "文案", "装饰", "参考"]
  },
  "ps": {                         // ← **原样** JSON.stringify 后喂 presetJSON
    "name": "占位（实测被忽略）",
    "width": 2480, "height": 3508, "units": "pixelsUnit",
    "resolution": 300, "resolutionUnits": "inchesUnit",
    "depth": 8, "scale": 1,
    "mode": "CMYK", "fill": "white",
    "profile": "Japan Color 2001 Coated",
    "guides": [ /* 由 meta.bleedMm + safeAreaMm 算出来 */ ],
    "artboards": []
  }
}
```

**为什么分两层**：`ps` 那层被 PS 直接读，**多一个它不认识的字段可能被忽略、也可能报错**
（这条**未实测**，所以按最保守处理）。`meta` 全是我们自己用的。
混着传 = 拿我们的字段去赌 PS 不报错。

**`createDocument` 的 `name` 参数另走**：`presetJSON` 里的 `name` **实测被忽略**
（回读是「未标题-n」），文档命名要用 `createDocument` 自己的参数。

### 3.3 建稿流程

```
用户选「A4 带 3mm 出血」
  → 插件由 meta.bleedMm / safeAreaMm 算出画布尺寸与参考线坐标
  → createDocument({ presetJSON })   ← **必须在 executeAsModal 里**
  → 参考线随建稿写入
  → 按 meta.layerStructure 建规范图层组
结果：从第一秒这稿就在正确轨道上 ⇒ 体检的出血判据天然成立
```

**参考线坐标的语义**：`template-probe` 传 `5/95/10/90`（画布 1000px）、
本轮传 `20/580/20/380`（画布 600px），回读都是 4 条且**位置与传入一致** ⇒
**按像素**传（不是百分比）。⚠️ 但 `doc.guides[i]` 只回 `_id`，**读不出坐标**
（这是既有的未解决项，见 §六）。

## 四、PSD 模板这条路：契约加法草案

> 按契约 §十，**新增 scope 属「加法」，不升版本**；两侧各自在 `DECISIONS.md` 记一条即可。
> **草案要点先写在这里，正式正文由两侧走 §十 流程落进契约。**

### 4.1 `manifest.json` 的 `scopes[]` 加一条

```jsonc
{ "id": "tpl", "label": "模板", "file": "tpl.json", "revision": 1, "count": 8 }
```

### 4.2 新文件 `tpl.json`

```jsonc
{
  "contract": "vellum-link/1",
  "scope": "tpl",
  "revision": 1,
  "generatedAt": "2026-10-17T03:40:00+08:00",
  "items": [
    {
      "id": 1,
      "name": "易拉宝 80×180（含3mm出血）.psd",
      "ext": "psd",
      "kind": "template",
      "size": 2400000,
      "width": 1772,          // ★ 模板画布像素。**必填**（与 §5.4 的"可为 null"不同，见下注）
      "height": 4134,
      "resolution": 150,      // ppi，读不到可 null
      "mode": "CMYK",         // 读不到可 null
      "usage": "易拉宝",       // 用途（可选）—— 插件据此筛/排
      "frameMm": "800×1800",  // 成品尺寸（可选）—— 给人看
      "bleedMm": 3,           // 出血（可选）
      "thumb": "thumb/p1.png",
      "missing": false,
      "modifiedAt": "2026-10-10T10:00:00+08:00",
      "absPath": "D:\\...\\模板\\易拉宝80x180.psd",
      "tags": ["易拉宝", "展架"]
    }
  ],
  "groups": []
}
```

> **注：`width`/`height` 对模板是"必填"** —— §5.4 允许素材的尺寸为 `null`（视频/PDF 等），
> 但模板的画布尺寸是**列表上唯一能让同事一眼分辨的信息**，读不到就不该收录。

### 4.3 缩略图命名空间

现有：任务库 `t<id>`、通用库 `b<id>`（防两库 `id` 各自从 1 起导致同名覆盖）。
**加法：模板库用 `p<id>`**（例 `p1.png`）。
⚠️ 对插件**透明** —— `asset.thumb` / `item.thumb` 一直是"镜像内相对路径"，
插件按字符串取图、**不解析文件名**（这条 LINK-LOG 2026-10-10 已确认）。

### 4.4 handoff 复用（**不走新通道**）

模板 PSD 的搬运**沿用既有 handoff**（唯一反向通道），只是换个 `scope`：

- 插件写 `req.json`：`{ "assetId": 1, "scope": "tpl", ... }`
- 软件侧在 **`tpl` scope 内**按 `assetId` 反查 ⇒ 拷成 `handoff/incoming.psd` ⇒ 写 `res.json`
- 插件 `app.open()` 打开它

**三条必须提醒软件侧的事**（会写进 `docs/54` 提示词）：

1. ⚠️ **`incoming.<ext>` 的 `ext` 必须跟着源文件走**（PSD ⇒ `incoming.psd`）。
   现有实现若写死 `.jpg` / `.png`，模板会全军覆没。
2. ⚠️ **`scope` 白名单要加上 `tpl`** —— 契约 §六 规则 8 写明「**未知取值 → `bad_request`**」，
   不加就会被插件收到"参数错误"。
3. ⚠️ **mtime 归零那一条（§六 规则 6b）对模板更重要** —— PSD 更大、拷得更慢，
   源文件往往是"很久以前做的模板"，带着旧时间戳必被自己的过期清理误杀。

**体积**：handoff 是把整份 PSD 拷进 **C 盘的 `PluginData`**。
⇒ 收录时就按 **≤ 20 MB** 卡住（拍板第 4 项），超了提示"请瘦身"（模板只留版式与图层结构，别打包大图）。

### 🔴 为什么必须改 `library.js`

素材库页的「库」标签是**完全由 `manifest.scopes[]` 动态生成**的（`tools/library.js` 顶部注释原话：
"软件侧将来加第三个库，插件零改动就能显示"）。这是当初特意做的优点 ——
但**正好和用户的要求冲突**：软件侧一写出 `tpl` scope，素材库页**会自动多出一个「模板」标签**。

⇒ 插件侧要**主动把 `tpl` 排除**在素材库之外，把它交给「新建稿」工具页。
（这也是本方案里唯一一处"必须违反既有自动机制"的地方。）
⚠️ 排除要**留痕**：`boot.log` 里记一行"排除 scope=tpl（属新建稿入口）"，免得以后有人以为是丢库。

### 「打开后叫 `incoming.psd`」的三个缓解选项（**要你选**）

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（我倾向）** | 打开后**面板上如实提示**："这是模板副本，请另存为你的文件名" —— 不做任何假装 | 同事要多点一次"另存为" |

### 11.1 Step 1 做了什么（v0.9.11）

**两个"看起来对、其实会静默出错"的地方**（加新库最贵的就是这类）：

1. 🔴 `flatten(scopeId, d)` 原来是**二元分派** `scopeId === "brand" ? flattenBrand : flattenTask`
   ⇒ 任何新 scope 都会**掉进 `flattenTask`**（拿 `d.projects` 去遍历 undefined）⇒ 表现为"新库一条都没有"。
   ⇒ 改成**按 id 显式分派 + 认不出时用结构兜底**。
   > 这条我在 LINK-LOG 里刚提醒过软件侧有同款，结果**我们自己代码里也有一份**。
2. 🔴 `scopeKind(data)` 只看结构：`tpl.json` 也带 `groups[]` ⇒ **被认成通用库**，
   界面按两层排、`flattenBrand` 拿 `items[]` 当 `assets[]` 全落空。
   ⇒ **优先读文件自己写的 `scope` 字段**（三个库都有），结构只作兜底；
     并且 `groups[] + items[]` 两张表 = 模板库（通用库没有 `items[]`）。

**`flattenTpl()` 的关键差别**：`items[]` 是**扁平**的，层级只由 `groupId` 指向，
所以路径是**从条目往上爬**（`groupPathOf`），不像通用库那样"从树往下走"。
输出字段与 `flattenBrand()` **逐字段对齐** ⇒ 素材库那套筛选、`groupTree()` 计数、
`dirlib` 面包屑**全都能直接复用**，不用为模板库单写一份。

**三种脏数据（宁可降级，绝不丢模板）**：`groupId` 为空 → 「未分类」；
`groupId` 指向已删的组 → 「未分类」；**成环** → `seen` 拦住、不爆栈，返回已爬到的那段。

**顺带**：按契约建议，被排除出素材库的 scope 在 `boot.log` **留一行痕**
（否则以后看日志会当成"丢库"来查；历史真发生过一次误判）。

### 11.3 留给 Step 3 的一个真问题：打开后的保存去向

⇒ 好处：**模板原件绝不会被改坏**；

### 12.3 打开流程（Step 3）

与素材库「置入」**同一条 handoff 通道**（契约 §六 规则 8），差别只在拿到文件之后：

（更彻底的做法是自动另存到工作区，但要写盘权限，留待用户拍板。）

## 十三、Step 4 落地 + 两个真实缺陷（v0.9.17）

### 13.1 按规范建稿（Step 4）

新增 `lib/specs.js`（**规范表唯一真相**）+ `ps.createFromSpec()` + 页面第二个模式「按规范建稿」。

| 规格 | 成品 | dpi | 模式 |
|---|---|---|---|
| 易拉宝 80×180 | 800×1800mm | 150 | CMYK |
| 展架 60×160 | 600×1600mm | 150 | CMYK |
| 海报 A3 / A4 | 297×420 / 210×297mm | 300 | CMYK |
| 名片 90×54 | 90×54mm | 300 | CMYK |

**算法**：成品 + 四边各 3mm 出血 = 画布；参考线落在**成品边**（画布内缩 3mm），四条。
例：800×1800mm + 6mm = 806×1806mm @150dpi ⇒ **4760×10665px**，参考线 18 / 4742 / 18 / 10647。

**为什么规范表放插件里**：PS 的新文档预设目录要 `fullAccess`、路径带版本号、还有竞态；
而 `presetJSON` 可以直接建稿（S68 已验）。⇒ 规范由我们的数据说了算，PS 只负责执行。
将来软件侧下发 `spec.json` 时接 `fromSpecJson()` 即可 —— **不要在别处再写第二份尺寸表**。

### 13.2 🔴 缺陷一：`app.open` 打开 CMYK PSD **必须先关原生对话框**

- **现象**：打开模板返回 `open ok=false err=The 文档 with an id of undefined does not exist.`
  —— 一句完全对不上原因的话。
- **真因**：模板是 CMYK，`app.open` 触发 PS 的「配置文件不匹配」**原生对话框**，
  在模态里卡住 ⇒ 宿主内部状态错乱，返回一个不存在的文档。
- **修法**：打开前 `app.displayDialogs = "dontDisplay"`，**用完还原**（S68 当年就是这么做的，
  我第一次实现 `openFile` 时漏了这一步）。
- 🔴 **连带教训（这次最贵的一条）**：那个卡住的对话框**不只毁掉当次调用** ——
  同一次自检里，**排在它前面的 S62/S63 也红了**（导出写盘"成功"但盘上没有、文字操作失败）。
  查了很久才发现是**同一轮里残留的模态状态**污染。
  ⇒ 通则：**原生对话框卡住会污染整轮**；凡是"一串本来好好的探针突然集体红"，先怀疑有对话框没关。

### 13.3 🔴 缺陷二：handoff 的 res.json 是**两段写**

- **现象**：`res ok=true`，但 `file ok=false name=incoming bytes=0`；而盘上明明躺着 14MB 的 `incoming.psd`。
- **真因**：软件侧**先写 `res.json` 说"完成"，之后才补 `file` 字段并拷文件**。
  我们在中间那一刻匹配上 reqId ⇒ `res.file` 为空 ⇒ 名字退化成不带扩展名的 `incoming` ⇒ 永远找不到。
- **修法**（`lib/handoff.js`）：
  · 等待期间**边等边重读 `res.json`**，把后补的 `file` 补上；
  · `file` 缺失时按**候选名**找（`incoming` / `incoming.psd` / `incoming.jpg` / `incoming.png`）；
  · 等待从 5s → **12s**（真机第一个模板 17MB）。
- 报告字段也补了 `res.file` —— 下次一眼就能看出"对方有没有给文件名"。

## 十四、真机事故：**UXP 不支持 CSS Grid**（v0.9.23，2026-10-17）

### 14.1 现象（这一条特别难查）

用户报「模板库放了 PSD，插件读不到」。查下来：

| 检查项 | 读数 |
|---|---|
| 磁盘 | 3 个 PSD 都在 |
| 软件库 `media.db` | 3 条都在 |
| 镜像 `tpl.json` | `items` 3 条，`count=3` |
| 插件状态栏 | **"模板库：3 个模板"** |
| 插件日志 | `items=3 list=3 cards=3`（卡片**建出来了**） |
| **屏幕** | **一片空白** |

⇒ **数据全对、卡片也建了，就是看不见**。而且 **一处报错都没有**（UXP 把渲染异常吞了）。

### 14.2 根因

`.nd-grid { display: grid; grid-template-columns: 1fr 1fr; }`
—— **UXP 不支持 CSS Grid**：容器与子项的 `offsetHeight` 全被算成 **0**，
于是整块区域"存在但高度为零"。

**唯一的线索就是高度**：延迟 400ms 量到 `bodyH=384`（父容器正常）但 `gridH=0 card0H=0`。

**修法**：改成 flex 两列 —— `.nd-grid{display:flex;flex-wrap:wrap;justify-content:space-between}`
+ `.nd-card{width:48.5%}`。改完 `gridH=305 card0H=145`，三张卡全部出现。

> 素材库的瀑布流一直是 flex（`.lib-col`），所以从来没踩到 —— **新写的这一页我图省事用了 grid**。

### 14.3 判据补强

- **S74 新增**：卡片建了必须**量得到高度**（首卡 > 40px，等布局落定最多 1.5s）。
  读数写成 `首卡高度=145px，须 > 40 —— 0 就是"建了但看不见"（UXP 不支持 CSS Grid）`。
- **运行时警报**：`renderGrid` 延迟 400ms 复查，高度为 0 就写 `boot.log` + 状态栏报警。
- **渲染异常可见化**：`renderAll()` 里 tabs / bar / grid / foot **各包一层 try/catch**，
  谁炸了写进 `boot.log`（`newdoc render FAIL where=...`）——UXP 吞掉异常，只能自己喊。

### 14.4 顺带修好的排查工具

`tools/manual/uipanel.py`：按**窗口尺寸**（`--size 422x732`）锁定 UXP 面板截图 / 点击。
为什么需要它：`shoot_win.py` 用 `--index` 选窗口，而 PS 的窗口**两次调用之间会重排**，
"列出来的 2 号"和"截图时的 2 号"经常不是同一个（实测截到过别的窗口）。

⚠️ 写它时又踩了一个自己的坑：**`ctypes` 的 EnumWindows 回调必须真的交给 `EnumWindows(cb, 0)`**。
我第一版直接 `cb(0, 0)` 调了一次 ⇒ 永远空列表，还误判成"沙箱里枚举不到窗口"（错了半天）。

## 十六、缩略图改正方形（v0.9.31）+ 一次暂存盘事故

### 16.1 用户拍板

### 16.2 🔴 为了这一件事，我连错了三版 —— 根因是"去量尺寸"

| 版本 | 做法 | 结果 |
|---|---|---|
| v0.9.26 | CSS 固定 `height: 174px` | 实际渲染 **168×174**（宽度是卡宽算出来的，不等于 174） |
| v0.9.27 | JS 读 `card.clientWidth − 12` 反推 | 仍是 168×174（`clientWidth/padding/border` 在 UXP 里的口径与假设不一致，差 6px） |
| v0.9.28–29 | JS 读 `th.offsetWidth` 写 `style.height`，加自证日志 | S74 读数 `inline height=""` ⇒ **一个字都没写进去** |
| v0.9.30 | 把"等布局 + 报警 + 校准"合成重试循环 | 仍 `168×174`（400ms 时先走"卡片高度为 0"分支并 `return`，校准从未执行） |
| **v0.9.31** | **CSS 固定卡宽 193px、缩略图 179px** | **正方形由尺寸算出来，零测量** |

**179 怎么来的**：`.nd-card` 是 `box-sizing: border-box`，宽 193 − padding 6×2 − border 1×2 = **179**。
缩略图盒子宽 179、高 179 ⇒ 必然正方形。

**为什么固定卡宽反而更好**：
- 面板 422 时 193 + 8(gap) + 193 = 394 = 内容宽，两列严丝合缝；
- 面板变宽时两列左右分开，卡片**仍是正方形**（旧的 `48.5%` 方案一变宽就不方了）。

🔴 **教训（与「估算 ≠ 真实」同族，但更狠）**：
前四版都把答案押在"在 UXP 里量一个尺寸"上，而**量尺寸的时机与口径都不可靠**
（布局落定 1–2s、`clientWidth` 口径差异、`style.height` 写入无效）。
**能算的不要量。** 尺寸确定的东西，应该在 CSS 里用算式写死，而不是运行时去问。

## 十七、🔴🔴 参考线大坑：`coordinate` 是**百分比**，不是像素（v0.9.37）

### 17.1 报障

用户截图：A3 建出来**只有一竖一横两条参考线**（应该 4 条），**而且离边缘很远**（3mm 出血本应几乎贴边）。

### 17.2 根因

`lib/specs.js` 给 PS 的是**像素**：

```js
guides: [
  { direction: "v", coordinate: 35 },      // ← 想表达 "左 35px"
  { direction: "v", coordinate: 3543 },
  { direction: "h", coordinate: 35 },
  { direction: "h", coordinate: 4996 },
]
```

而 PS 的 `presetJSON.guides` 里 **`coordinate` 是百分比（0–100）**：

- 权威依据①：PS 自带 `New Doc Sizes.json` 里 HDTV 1080p 的写法是
  `{direction:"h",coordinate:5}, {…10}, {…90}, {…95}` —— 5%/10%/90%/95%，明显是百分比；
- 权威依据②：社区资料原文「**You can specify guides by percentage of width and height.**」

⇒ PS 把 3543 当成 **3543%** ⇒ 落到画布外 ⇒ **只剩左、上两条可见**。

### 17.3 🔴 为什么三轮自检都没抓到（最贵的假绿）

S68 / S75 的判据是 **`document.guides.length === 4`** ——
**即使两条在画布外，它照样回 4**。所以读数一直是绿的。

而"读坐标"这件事在 UXP 里**根本走不通**（本轮全部试过）：

### 17.4 修法

```js
const pctX = (bleedPx / width) * 100;   // A3：3mm / 303mm ⇒ 0.978%
const pctY = (bleedPx / height) * 100;
guides = [
  { direction:"v", coordinate: r3(pctX) },        { direction:"v", coordinate: r3(100-pctX) },
  { direction:"h", coordinate: r3(pctY) },        { direction:"h", coordinate: r3(100-pctY) },
];
```

留 3 位小数 ⇒ 回算误差 **< 0.02px**。

| 规格 | 画布 px | 出血 px | 竖线 % | 横线 % | 回算 px |
|---|---|---|---|---|---|
| A3 297×420 @300 | 3579×5031 | 35 | 0.978 / 99.022 | 0.696 / 99.304 | 35 ✓ |
| 易拉宝 800×1800 @150 | 4760×10665 | 18 | 0.378 / 99.622 | 0.169 / 99.831 | 18 ✓ |
| 名片 90×54 @300 | 1134×709 | 35 | 3.086 / 96.914 | 4.937 / 95.063 | 35 ✓ |

### 17.5 判据换代（关键是**不再写死数字**）

**离线断言 54**（原来断 `v18,v4742,h18,h10647`）改成断**语义**：

1. 4 条**全部**落在 `0 < coordinate < 100`（百分比区间）；
2. 左右两条相加 = 100，上下两条相加 = 100（±0.01）；
3. 按百分比**回算的 px ≈ `bleedPx`**（±1px，证明它确实落在成品边）。

⇒ 以后谁把单位改回像素，第 1 条立刻红。**写死具体数字反而会被"看起来对"的值蒙过去**。
