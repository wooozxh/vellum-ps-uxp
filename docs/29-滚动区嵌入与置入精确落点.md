## 一、素材库改成「固定区 + 单滚动区」

**用户原话**：「滚动条应当嵌入瀑布流中，不然还是会导致置入下面的图还要跑回顶部点击置入」。

v0.3.2 把详情/置入块挪到网格上方只是"少滚一点"，**整页仍然一起滚** —— 素材一多，
置入块照样被推出视野。这次把页面拆开：

```
.scroll（外壳，不再滚）
  .screen.active
    .s-lib   ← position:absolute; left/top/right/bottom:0; display:flex; flex-direction:column
      .lib-top       ┐
      .lib-meta      │ 固定区（flex: 0 0 auto）—— 永远可见
      .lib-metanote  │
      .lib-bar       │
      .lib-foot      ┘  ← 置入按钮在这里
      .lib-body      ← 唯一的滚动区（flex:1 1 auto + min-height:0 + overflow-y:auto）
        .lib-grid（瀑布流）
```

四条要点：

1. **为什么用绝对定位撑满而不是 `height:100%`**：`.screen` 是高度 auto 的 block，
   `height:100%` 在那条链上解析不出高度（会退化成 auto），必须锚到 `.scroll` 的 padding box 上。
   ⇒ 顺带给 `.scroll` 加 `position: relative`。
2. **`.fsel-pop` 不受影响**：下拉浮层的包含块是 `.fsel-wrap`（它自己有 `position:relative`），
   而 `.scroll` 仍是裁切容器（`overflow` 非 visible 就裁）⇒ **旧的不变量①（浮层必须落在
   `.scroll` 内）依旧成立**，自检 S20c 不用改。
3. **`min-height: 0` 是硬要求**：flex 子项默认 `min-height:auto`，不写它 `.lib-body` 会被
   内容撑高，"滚动区"就不生效（这类"看着像但滚不动"的坑很难归因）。
4. **离线断言 45 守门**：`.s-lib` 的绝对定位+flex 纵向 / `.lib-body` 的 overflow / 固定区组的
   `flex:0 0 auto` / `.scroll` 的定位上下文 —— 缺任一条界面就退化成"整页滚动"，而那种退化离线看不出来。

## 二、置入尺寸不对 —— 根因是「PS 按物理尺寸置入」

### 2.1 现场读数（真机日志，素材 1500×1500 置入 1920×1080 画布）

```
anchor=mc  off=0,0      expect=210,-210,1710,1290   landed=693,360,1053,720  hit=false
anchor=tl  off=-210,210 expect=0,0,1500,1500        landed=483,570,843,930   hit=false
anchor=br  off=210,-210 expect=420,-420,1920,1080   landed=990,150,1350,510  hit=false
anchor=tr  off=210,210  expect=420,0,1920,1500      landed=990,570,1350,930  hit=false
```

`landed` 的宽高**恒为 360×360** —— 而素材是 1500×1500、插件期望的也是 1500×1500。

### 2.2 归因（两条独立读数交叉验证）

| 读数 | 来源 | 值 |
|---|---|---|
| 源图 `XResolution` | 本机解析 `图一(1).jpg` 的 Exif（`XResolution=300, ResolutionUnit=inch`） | **300 ppi** |
| 尺寸比值 | `360 / 1500` | **0.24 = 72 / 300** |

⇒ **PS 的「置入嵌入对象」是按「物理尺寸」放的，不是 1:1 拷像素**：
源图 5 英寸（1500 px @300ppi），放到 72 ppi 的画布上 = **5 × 72 = 360 px**。

⇒ 于是 `offset` 这套定位方式**建立在一个错的尺寸假设上**：插件以为素材在画布上是 1500 px 宽、
按 1500 算锚点，而画布上实际只有 360 px ⇒ **尺寸与位置一起错**。

> 附带修正一个之前的结论：S24/S25 得出"置入不缩放"是在**同 ppi 前提**下测的
> （临时文档 72ppi + 自造素材），换到真素材（300ppi）就露馅了。
> ⇒ **"在某个前提下达成的结论"必须连着前提一起记**，否则它会伪装成普适规律。

### 2.3 修法：不猜 ppi，改成**自校正**

```
置入（无 offset）→ 量实际 bounds → layer.scale(目标宽/实际宽, 目标高/实际高)
→ 再量 → layer.translate(目标中心 − 当前中心) → 再量 → 与目标矩形逐边比对（±1px）
```

- 用到的两个 API 是**官方文档化**的 DOM 方法（`ps_reference/classes/layer`）：
  `Layer.scale(widthPercent, heightPercent)` / `Layer.translate(horizontalPx, verticalPx)`。
  **不用 batchPlay 的 `transform` 描述符** —— 那个 `_target` 形状本项目没有真机证据，
  属于"ActionDescriptor 禁止猜"的范围。
- `scale()` 的**锚点文档没写明** ⇒ 代码里**不假设它**：缩放后**重新读一次 bounds**，
  再按"中心对齐目标中心"算 translate 差值。⇒ 锚点是什么都不影响最终结果。
- ⚠️ **只在 `changed`（图层真多出来了）时才校正** —— 万一置入失败，
  校正会把用户**原有的**图层缩放/挪走，那是不可逆的破坏。
- 返回结构新增 `fix: { ok, hit, scaled, steps, before, after }`，`steps` 把
  `scale=…%` / `translate=…` 的实参原样带进日志（排障时不必再猜）。

### 2.4 位置语义的变化（**这是一处行为变更，需知悉**）

- 旧（`offset` 路径）：`offset` 是相对"默认落点"（有选区=**选区中心**，无选区=画布中心）的位移。
- 新（`targetRect` 路径）：目标矩形由 `anchorOffset()` 的 `x/y` **直接给出**（画布绝对坐标）
  ⇒ **与选区无关**，位置可预测。
- 代价：v0.3.0 那个"有选区时贴选区中心"的语义**不再自动生效**；
  若以后要"贴选区的角"，应把选区作为**区域参数**传进 `anchorOffset`（改一处纯函数即可）。

### 2.5 仍未定的产品决策（留给用户）

现在置入尺寸 = **素材原始像素尺寸（1:1）**。
把 1500×1500 放进 1920×1080 画布，"居中"会上下各溢出 210 px —— 这是"原尺寸"的必然结果。
若想要"适应画布"，应另做一档（**不**改默认，避免又变成"尺寸不对"）。

## 三、素材同步：插件侧本来就是自动的

用户问「素材刷新同步是纯手动吗」。**查下来插件侧是自动的，手动的是软件侧"写镜像"那一步。**

- 插件：`mirror.watch()` **每 3 秒**读一次 `manifest.json`，比对各 scope 的 `revision`，变了就重渲染。
- 证据（真机日志，同一次会话）：
  ```
  03:48:32 / 03:48:44 / 03:48:45 / 03:48:53  library manual refresh …（用户连点了 4 次，rev 一直还是 5）
  03:48:59  library watch first=false revs=task:6        ← 这一次是**插件自己**发现的
  03:48:59  library scope … rev=6 items=19 via=change    ← via=change 即"轮询发现"，不是人点的
  ```
  ⇒ 用户连点刷新看不到新素材，是因为**那时软件侧还没把新数据写进镜像**；
  两分钟后镜像更新，插件**自己**就刷出来了（`items` 1 → 19）。
- ⇒ 结论：这是**软件侧的需求**（何时重写镜像），已整理成可直接转发的需求提示词（见交付说明）。

## 五、附：软件侧并行开发通用库的影响评估（回答用户第 4 问）

**不会影响。** 唯一耦合点仍是**已冻结的契约**（`vellum-link/1`）：

- 插件侧的"库列表"完全由 `manifest.scopes[]` 生成 ⇒ 软件侧新写一个 `brand` scope，
  插件**零改动**就会多出"通用素材库"入口（v0.3.2 已加"只有 N 个库"的如实提示兜底）。
- 库的"形态"由 `mirror.scopeKind()` **按数据形状**判（`projects`→task / `groups`→brand），
  **不写 `if (scopeId === "task")`** ⇒ 软件侧加库、改名都不会静默失效。
- 三条**需要先公告**的契约可见面（改之前说一声即可）：
  ① 三层分组（现在两级）；② `asset.source` 新取值；③ 素材字段增减（`width/height` 是置入的硬依赖）。
- ⚠️ **一个真实的干扰**：软件侧开发期间会**不断重写真镜像**，而自检跑在真镜像上 ⇒
  自检读数会跟着变（比如本轮 `task` 从 6 项目/1 条变成 7 项目/19 条，是正常的，不是回归）。
  要拿稳定读数就用假桩 + `--force`，或挑软件侧空闲时跑。
