## 一、通用库不再画重复的「来源」行

**现象**：一级是「全部」时，筛选区同时出现
`[全部][公司素材][我的收藏]` 和 `[全部][公司][我的]` —— 两者说的是同一件事。

**根因**：`brand.json` 的**顶层分组本身就是按来源分的**（软件侧 docs/47 §3① 明确：顶层固定
「公司素材 / 个人收藏」），而 `asset.source`（company / user）是同一维度的另一种叫法。

### 🔴 判据的第一版错了：靠"命名巧合"

```js
// ❌ 第一版
const srcCovered = srcs.every(s => topNames.some(t => t.indexOf(s.label) >= 0));
```
想的是「"公司" ⊂ "公司素材"、"我的" ⊂ "我的收藏"」—— 而**软件侧的顶层叫「个人收藏」，不叫「我的收藏」**，
`indexOf("我的")` 直接落空 ⇒ 判据恒为 false ⇒ 该行照画。**真机上一跑就露馅。**

### ✅ 改成问本质：**两种切法是不是同一个划分**

```js
const srcRedundant = (() => {
  if (tree.length < 2 || tree.length !== srcs.length) return false;
  for (const t of tree) {
    const inT = S.items.filter(it => it.group === t.name);
    if (mirror.sourceSummary(inT).length !== 1) return false;  // 这个顶层组里混了别的来源
  }
  return true;   // 组数 === 来源种类数，且每组单一来源 ⇒ 按组切 == 按来源切
})();
if (srcs.length > 1 && !srcRedundant) { /* 才画 */ }
```

⇒ 不依赖任何命名。**将来若顶层分组不再按来源分**（比如改成「海报 / logo / 其它」而来源混在其中），
这一行会**自己回来**，不会静默丢掉一个筛选维度。

- **卡片上的来源角标保留**（`showSrc` 那套没动）—— 角标标的是**每一张素材**、不占筛选区版面，是另一回事。
- 离线断言 **47** 守门（`40`/`47` 都印筛选区签名，失败时能一眼看出画了哪些行）。

## 二、瀑布流：容器高度 = 盒宽 × 缩略图高宽比

### 2.1 可行性的前提（先验，不然白做）

**软件侧的缩略图是"长边 320、等比缩放"，不是裁成正方形** —— 本机读了镜像 `thumb/` 里全部 PNG 的 IHDR：

```
b19.png 146x320   b2.png 240x320   b20.png 207x320   b21.png 134x320
b78.png 226x320   t108.png 155x320  t1.png 78x160    b70.png 60x59
t110/t112/t113 … 320x320（原图本来就是正方形）
```
⇒ 比例信息完整，瀑布流做得成。

### 2.2 结构：两列各自纵向堆叠（不是 flex-wrap）

```css
.lib-grid { display: flex; align-items: flex-start; margin: 0 -5px; }  /* 不再 flex-wrap */
.lib-col  { width: 50%; display: flex; flex-direction: column; }
.card     { width: 100%; padding: 0 5px 10px; }                        /* 占满所在列 */
```
分派在 JS：每张卡片投给**当前累计高度较小**的那一列（`acc[0] <= acc[1] ? 0 : 1`），
`grid` 上写 `data-cols="556/677"` 便于排障。

**为什么不能 flex-wrap**：wrap 是"行高 = 本行最高"，短卡片下面会留一大片空隙 —— 那就不是瀑布流了。

### 2.3 🔴 高度：**推算**会错，必须**量了再算**

第一版在渲染时按面板宽度**推算**盒子宽度：`imgW = round(bodyW/2) - 5`。
`.lib-grid`(负外边距) → `.lib-col`(50%) → `.card`(100% + 左右各 5px 内边距) 三级下来，
任何一处差一点都会放大成十几像素 —— 真机实测**推算 201px、实测 189px，差 12px**。

⇒ 加了 `relayoutThumbs()`：**布局落定后，用每个盒子自己的 `offsetWidth` 重算一遍高度**
（轮询最多 20×50ms，令牌与 `loadThumbs` 同源，重渲染/切库/卸载立刻停手）。
并把真正量到的宽度写进 `grid[data-boxw]` —— 既是排障读数，也是自检等"布局就绪"的信号。

### 2.4 封顶与保底

`THUMB_MIN_H = 72` / `THUMB_MAX_H = 380`：不封顶的话一张 1:5 长图会把整列拉飞；
不保底的话 5:1 扁图会变成一条缝（名称和元信息全挤在一起）。
`asset.width/height` 缺失时先留 CSS 保底 120px，图片加载完再用 `naturalWidth/Height` 校正一次。

## 三、S27 这条探针改了四次（每一版都是同族纪律的现场版）

| 版本 | 问题 | 改成 |
|---|---|---|
| 1 | **判据太弱**："盒子高度不止一种" | **逐张卡片比**「盒高 = 盒宽×素材高宽比」 |
| 2 | **判据太弱②**：目标矩形取 400×400（= 画布），而 PS 超画布会缩到适应 ⇒ 原始置入恰好也是 400×400，**校正没生效也会通过** | 目标改成 `200×200@(50,60)`（尺寸与位置各有一个位移量要凑） |
| 3 | **时机太早**：`relayoutThumbs` 是异步的，断言量到的是**推算值**（201 vs 189） | 先等 `data-boxw` 出现（布局落定信号）再量 |
| 4 | **样本没区分度**：库里只剩 1 条素材 ⇒ "两列分派"和"按比例"都验不到 | 主动切到**条目最多的那个库**再验（`scopes[].count` 最大的） |

最终读数（brand 库、4 张、比例各异）：
```
卡片=4（挂在列里的=4）　本轮验的库=brand　列容器=2（须 2）
逐张比对「盒高 = 盒宽×素材高宽比」：4/4 命中　两列高 556/677（合计 1233）·均衡=true
```

### 其余四处连带修正

1. **`libCards` 的作用域**：第一版把它 `const` 在 S20 的 `try` 块里，而 S20d/S20e 在**各自的 try 块**
   ⇒ 真机直接 `libCards is not defined`。⇒ 提到 `run()` 顶层的帮助函数区。
2. **"等网格渲染完"退化成"网格存在就行"**：网格直接子节点**恒为 2**（两列容器），
   `el.children.length > 0` 永远为真 ⇒ 全部改成递归数 `.card`。
3. **`data-scope`/`data-rev` 之后又多一个身份字段**：数卡片不能再用 `children.length`（同上）。
4. 离线断言 24/37/40 跟着实现更新（`.card` 50% → `.lib-col` 50% + `.card` 100%；
   数卡片改递归）—— **判据换的是结构，不是把阈值放宽去迎合代码**。
