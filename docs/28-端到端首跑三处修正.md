## 〇、先说一个前提：`library/` 里现在躺着的是**真镜像**

用户报"通用素材库入口丢失"时我去看磁盘，发现目录已经被**真 VellumDesk** 接管了：

```
manifest.json   381 B   Oct 11 03:00   ← generator.app = "VellumDesk", version 1.9.7（无 fixture 标记）
task.json      2073 B   Oct 11 03:00   ← 真项目：6 个项目 / 1 个任务包 / 1 条素材 / thumb=t110.png
brand.json     2619 B   Oct 11 02:31   ← ⚠️ 这一份还是**我的假桩**留下的（stale）
thumb/         t110.png 87339B …       ← 真缩略图
handoff/       req.json + res.json     ← 握手已经真跑过
```

**这条事实决定了本轮两件事**：① 用户报的 ② 其实是"镜像里没声明"，不是插件丢了入口；
② 自检里所有"写死 fixture 数字/文件名"的地方（S19 的 `taskRows===3`、S21 的 `t401.png`）
**必须改掉**，否则真机上会报一堆与真因无关的 FAIL。

## 一、①「原图已就位但拿不到可置入的文件句柄」

### 现场（不是我猜的，是磁盘与日志的原始读数）

```
# 插件侧 boot.log
02:58:11  library handoff req ok=true reqId=r-20261011T025811-1a09 assetId=110 scope=task created=false
02:58:12  library handoff incoming ok=false name="incoming.jpg" bytes=0 entry=false err=文件不存在：incoming.jpg
```

```jsonc
// handoff/res.json（真软件写的，原样）
{ "contract": "vellum-link/1", "reqId": "r-20261011T025811-1a09", "ok": true,
  "file": "handoff/incoming.jpg", "size": 627927, "error": null,
  "at": "2026-10-11T03:00:30+08:00" }
```

```
# handoff/ 目录实况
req.json   145 B  02:58
res.json   190 B  03:00
（没有 incoming.jpg）
```

**⇒ `res.json` 报 `ok:true / size=627927`，但 `handoff/` 里根本没有那个文件。**

### 我这边有两个错，都得改

**(a) 判据：看一眼就判死，把"竞态"和"软件没拷"混成了一个现象。**
`fetchIncoming()` 原来读一次就返回。而软件侧很可能「先写 `res.json`、后拷文件」——
那 1 秒的差就足以让插件报"文件不存在"，与"软件压根没响应"**长得一模一样**。

修法：看到 `res` 之后**再轮询 5 秒（每 250ms）等文件落盘**（`FILE_WAIT_MS`）。
这层兜底**不依赖对方守约**。

**(b) 反馈：说了一句**错位的**话。**
原文案是「✗ 原图已就位但拿不到可置入的文件句柄」—— 而**文件压根没到**。
「判据正确 ≠ 反馈正确」：一句错位的描述会把排查方向直接带偏（我就被带过一次）。

改成：
```
✗ 取不到可置入的文件：handoff/incoming.jpg 找不到（等了 502ms）
  —— VellumDesk 回复 ok=true · size=627927，但文件没落盘。
     请它按「先拷文件、后写 res.json」的顺序来（契约 §六）
```
失败文案现在能**区分**三种原因：`res` 说 ok 但文件不在（对方没拷成）/ `res` 说 ok:false（带它的 error 原文）/ 根本没等到 res。

### 契约同步（跨项目，按 §十 流程）

在 `LINK-CONTRACT.md` §六 补了**两条规则**（加法，不升版本）：

| 规则 | 内容 |
|---|---|
| **6｜顺序** | **先把 `incoming.<ext>` 真正落盘，再写 `res.json`**；**拷贝失败必须写 `ok:false` + `error`，不要乐观地写 `ok:true`** |
| **7｜`file` 语义** | 它是**镜像内相对路径、带 `handoff/` 前缀**（`"handoff/incoming.png"`），插件取 **basename** 在 `handoff/` 下找 |

并在 `LINK-LOG.md` 发了 `[插件侧]` 条目，附上上面全部原始读数 + 三条待对方确认的事
（拷贝目标路径 / 同一 reqId 的 res 被写过两次是否有意 / brand scope 何时写出）。

> ⚠️ **这条还没收口** —— 软件侧未回复。**若它确实没拷文件，插件侧的 5 秒兜底也救不了**，只是让失败原因更清楚。

## 二、②「通用素材库入口丢失」——不是插件丢了入口

`manifest.json` 的 `scopes` **只声明了 `task`**：

```json
"scopes": [ { "id": "task", "label": "任务库", "file": "task.json", "revision": 5, "count": 1 } ]
```

而插件侧的库 tab **完全由 `scopes[]` 生成**（这是设计如此：软件侧加库插件零改动）。
⇒ 只渲染 1 个 tab 是**正确行为**，通用库要等 VellumDesk 写出 `brand` scope 才会出现。

**但"正确行为"不等于"用户看得懂"** —— 用户看到的就是"入口不见了"。所以加了一行如实提示
（只在不足 2 个库时显示）：

```
镜像里目前只有 1 个库（任务库） —— 其余库要由 VellumDesk 写进 manifest.scopes 才会出现
```

## 三、③ 置入区挪到瀑布流上方（用户明确要求）

用户原话：「置入功能在瀑布流最下面，加入素材特别多，选择上面的素材后还要滚到最下方选择置入，
不太方便 可以把置入放在顶部（**库选择和目录筛选下方，瀑布流上方**）」

做法：把整个「详情 + 置入」块（`refs.foot`）从网格**下面**移到网格**上面**，DOM 顺序变成：

```
库切换 + 项目下拉 + 刷新
镜像元信息
筛选行
── 详情 / 置入（选中素材的信息 + 置入按钮 + 落点九宫格）──   ← 挪到这里
── 网格 ──
```

CSS 只改了 `.lib-foot` 的 `margin-top: 4px` → `margin: 0 0 10px`。
未选中素材时该块只有**一行提示**（改成「在下面选一张素材 —— 这里会出现置入按钮与落点」），不占地方。

**代价（如实说）**：选中素材后这个块约 150px 是常驻的，网格会被推下去一些。
这是"置入永远看得见"换来的 —— 若之后觉得网格太矮，可以再把它做成可折叠。

⚠️ 离线断言 41 用**实际挂载出来的 DOM 顺序**钉死这条（比读源码里的书写顺序硬）。

## 四、🔴 本轮真正的重点：自检必须**跟镜像无关**

真镜像一进来，旧自检立刻暴露出一类问题：**它绑死在我的 fixture 上**。

| 位置 | 原来写死 | 后果 |
|---|---|---|
| S19 判据 | `taskRows===3 && brandRows===4 && srcSig==="company:3\|user:1"` | 真镜像 1 条素材 ⇒ **FAIL（与真因无关）** |
| S21/S22/S24/S25 测试文件 | `t401.png` | 真镜像叫 `t110.png` ⇒ 找不到文件 |
| S20c/S20d 前置 | 直接读 `library/brand.json` | 磁盘上躺着 **stale brand.json** ⇒ 自检去操作一个**界面上根本不存在的库** ⇒ **假 FAIL** |
| S20e 的"收窄" | 取"素材最少"的项目 | 真镜像有 5 个**空包项目** ⇒ 点下去网格变空态块、量不到 ⇒ 假 FAIL |
| S20e 的"切到通用库" | 无脑切 | 镜像没 brand ⇒ 假 FAIL |

全部改掉：

1. **期望值一律从原始 JSON 自己数**（`countAssetsDeep` / `expSubRows` / `expSrcCounts`），
   镜像没声明 `brand` scope ⇒ 那一半记**「不适用」**，**不判失败**。
2. **测试文件从镜像里挑**（`testThumbFile()` 取第一条素材的 `thumb`），不再写死文件名。
3. **S20c/S20d 先查 `manifest.scopes[]` 有没有声明 brand** ——
   **哪些库存在，唯一依据是 scopes，不是"目录里有没有那个文件"**。
   （stale 文件的存在与否不该影响自检的结论。）
4. S20e 只挑**有素材**的项目验收窄；并新增一条断言：**空项目也必须出现在选项里**
   （这正是 `projectOptions()` 读**原始 `projects[]`** 而不是读"已展平的素材树"的理由）。
5. 「不适用」统一记成 `rec(name, true, "【不适用】…")` ——
   这样 **FAIL 只剩"真的有东西坏了"**，而不是"这个镜像没有那个样本"。

### 附带：给假软件桩加了一道**安全闸**

真软件上线后，**真镜像与假 fixture 躺在同一个目录**。以前 `node tools/fake-vellumdesk.cjs`
是"随手一跑"，现在同一句命令会**把用户的真项目/真素材整个换成 fixture** —— 而且看起来是成功的。

加了闸：本桩写的 manifest 带 `generator.fixture = true`，真软件的不带 ⇒ **不认识就 `exit 3`**，
要覆盖必须显式 `--force`（`--clean` 同样受保护）。
安全闸抽成了**纯函数** `canWrite(manifestPath, force)` —— 因为本环境**起不了子进程**
（`spawnSync` 报 `EBUSY`），纯函数才测得了；再加一条源码级断言确认**两条写路径都接了闸**。
