## 一、`not_found` —— 取证后确认是软件侧（handoff 没按 scope 查）

### 1.1 现场读数（同一分钟，四条连在一起，对照最清楚）

```
15:49:18  handoff req  assetId=85   scope=brand → res ok=false  err=not_found
15:49:22  handoff req  assetId=112  scope=task  → res ok=true   incoming.jpg 627927 B  ✓
15:49:26  handoff req  assetId=56   scope=brand → res ok=false  err=not_found
15:49:30  handoff req  assetId=59   scope=brand → res ok=false  err=not_found
```

`handoff/req.json` 原文（插件写的）：
```json
{ "contract": "vellum-link/1", "reqId": "r-20261011T154930-6848",
  "assetId": 59, "scope": "brand", "at": "2026-10-11T15:49:30+08:00" }
```
`handoff/res.json` 原文（软件写的）：`{ "ok": false, "file": null, "size": null, "error": "not_found" }`

### 1.2 归因

- **插件侧没传错**：`scope` 来自 `flattenBrand()` 给每条条目打的 `scope:"brand"`，与缩略图命名空间
  `b<id>` 同源；同一分钟任务库那条一次就通，说明 handoff 链路本身正常。
- **软件侧的按 id 反查没有按 scope 限定**。契约 §六 的拓扑图确实只写了"按 assetId 反查 absPath"
  —— **这一条是插件侧的文档漏写**（现在已在 `LINK-LOG` 里补上建议）。
- ⚠️ **真正的风险不是 not_found 而是串库**：§5.5 早已写明两库 `asset.id` **各自从 1 起**，
  只按 id 查一旦撞上，会拷回**另一张图** —— "置入成功但图不对"极难归因。现在只表现为 not_found，算运气好。

### 1.3 处理

- `LINK-LOG.md` 发 `[插件侧]` 公告：附全部原始读数，请软件侧把反查键改成 **(scope, assetId)**；
  并给出契约 §六 的建议增补（`scope` 必填、必须在该 scope 内反查）。
- **插件侧顺手改掉反馈**：失败文案从光秃秃的 `not_found` 变成
  `✗ 取原图失败：not_found　〔请求：scope=brand · id=59〕` ——
  用户报障时这一行就是**能直接转给软件侧的原始读数**（这次就是靠它一眼定位的）。
  （老纪律：失败原因必须出现在用户看得见的地方，且带下一步动作。）

## 二、缺 `width`/`height` 的兜底（PSD / PDF 会碰到）

### 2.1 问题

契约 §5.4：`width`/`height` **可能为 null**（非图片 / 探尺寸失败）。而 v0.3.3 起的"精确落点"
**就是拿这两个数算目标矩形的**。以前 `anchorInfo()` 算不出来会返回 `ok:false`
⇒ 调用方**什么都不传** ⇒ 退回最原始的置入（**画布居中、尺寸交给 PS**）
⇒ 用户选的九宫格被**静默忽略**。

**问题的本质不是"缺尺寸"，而是"缺尺寸时整个功能一起放弃"。**

### 2.2 修法：能定位就定位，量不出尺寸就不动尺寸

`library.js` 在"画布尺寸有、只是素材缺尺寸"时传 `anchorPlace: { anchor, docW, docH }`；
`ps.placeFile` 新增分支：

```
置入 → 量出 PS 给的实际尺寸 (aw, ah) → 用 aw/ah 当作"目标尺寸"去算锚点矩形
     → applyLayerRect（宽高恰好等于 aw/ah ⇒ scale 那一步自然被跳过）→ 只做 translate
```

⇒ **尺寸保持 PS 给的样子**（本来也无从校正），但**落点照样落在你选的格子上**。
`fix.byActualSize = true` 把"这次是只定位"这件事带进日志。

### 2.3 缩略图那条（用户特意点出）

那些卡片的**盒子高度**是拿 `asset.width/height` 算的 —— 为 null 时算不出来，于是永远停在
CSS 保底的 **120px**，在一屏瀑布流里格格不入（**而它们的缩略图明明是有比例信息的**）。

⇒ 加一条回落 `thumbBoxHFor()`：**素材没尺寸时，改用缩略图自身的 `naturalWidth/Height`**；
`loadThumbs` 读完所有图后再触发一次重算（有 asset 尺寸的卡片两次算出来相同，不会跳）。

### ⚠️ S28 第一版又是"样本没有区分度"

第一版用 **400×400** 画布，而缩略图换算后超出画布 ⇒ PS 把它**缩到填满** ⇒ 素材 = 画布 =
`落点 0,0 (400×400)`，判据 `0+400 == 400` **是碰巧成立的** —— "贴右上"和"贴左上"都是 0,0，
**锚点生没生效根本测不出来**。

⇒ 画布改成 **2000×2000**（> 缩略图换算后的 ~907，于是 PS **不缩放**），
并要求 `fin.left > 0`。这样"右上"必须是 `1078,0`，与"左上"的 `0,0` 明确区分开。

> 这是同一条纪律的**第三次**现场版（S26 的"目标矩形取成画布尺寸"、S27 的"库里只剩 1 条"）。
> 造反例时先问一句：**这份数据能让实现错、断言仍然通过吗？**
