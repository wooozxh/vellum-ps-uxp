> 2026-10-17。用户与软件侧沟通后达成共识：**模板功能 + 通用素材库都要做多层目录**；
> 软件侧正在画 HTML mock，插件侧要评估实现方法并出 mock。

## 一、结论：**能做，而且骨架已经在**

不是"要从零加功能"，而是"把已有的一层壳撑开"。三条证据（都在现有代码里，不是推测）：

| # | 证据 | 位置 |
|---|---|---|
| ① | 通用库**已经在解析 `parentId` 建父子关系**，并展平成 `group`（父）/ `sub`（子）两个字段 | `lib/mirror.js` `flattenBrand()`（L143–190） |
| ② | 展平结果里**已经带 `groupPath` 与 `crumb` 两个「路径数组」** —— 这就是多层目录的天然载体 | `flattenBrand()` L173–174 · `flattenTask()` L122–123 |
| ③ | 任务库的 `crumb` **已经装了三层**（项目 / 任务包 / 稿）⇒ "数组表示层级"这套早已在跑 | `flattenTask()` L123 |

也就是说：**数据层已经通到"任意层"，只是 UI 只把 `groupPath` 前两项画成了 chips**。

两条要同时说清的**限制**（现在真实存在）：

- 🔴 **契约 §5.3 明确写着「软件侧两层封顶，不会产出三层以上」** ⇒ 真给三层数据，插件侧**会把第 3 层压平成顶层**
  （`flattenBrand()` 结尾的兜底循环：不丢素材，但**层级丢了**）。⇒ **要放开多层，这是契约变更。**
- ⚠️ **任务库的四层（项目→任务包→稿→素材）是业务语义，不是"目录"** —— 建议**保持不动**（见 §五 待拍板 3）。

## 二、三个方向（按真实面板规格 340×580 出 mock）

> 图：`preview/multi-level-dir-mock.png`（源 `preview/multi-level-dir-mock.html`，Edge 无头渲染）
> 用插件**暗色主题**与**真实两列瀑布流卡片**绘制；示例走真实场景（品牌视觉 → Logo → 基准式样，**三层**）。

| | A · 常驻目录树 | **B · 面包屑下钻** | C · 多级筛选 chips |
|---|---|---|---|
| 形态 | 左侧固定树（104px）+ 右侧网格 | 顶部面包屑 + 子目录区 + 全宽网格 | 每级一行 chips（缩进）+ 网格 |
| 网格可用宽 | **216px**（两列各 103） | **322px**（与现在完全一样） | 322px，但被筛选区吃掉高度 |
| 层级可见性 | 一眼看全 | 靠面包屑（可点回任意级） | 靠 chips 行 |
| 跨层跳转 | 最快（一跳） | 面包屑直跳 | 需重选 chip |
| 跨层**多选** | ✗ | ✗ | **✓ 独有** |
| 层数增长成本 | 树可滚动，尚可 | **零成本**（同一块渲染任意层） | 每级 +27px，5 级吃掉 135px |
| 同事学习成本 | 中（要理解树） | **低**（= 资源管理器双击进文件夹） | 中（"筛选"≠"目录"的两种心智） |

### 推荐 **方向 B**

四条理由：

1. **窄面板的唯一可行解**。340px 下面向 A 的网格只剩 216px，缩略图基本看不清 ——
   这正是 `docs/10 §112` 早就记下的结论："PS 面板窄而高，**不采用「左列表 + 右内容」**，右侧内容区会被挤没"。
2. **层数不设限对 UI 零成本**。第 3、4、5 层走同一段渲染逻辑，不像 chips 那样"每级吃一行"。
3. **零学习成本**。就是"双击进文件夹"，和同事每天用的资源管理器一致。
4. **不牺牲缩略图尺寸**：网格宽度与现在完全相同，**已验收过的瀑布流一行不用改**。

C 的价值在于**跨层多选**（同时看"基准式样 + 反白版"）—— 这是 A/B 都做不到的。
⇒ **建议：B 做成主形态；C 作为 B 的可选第二模式**（不单独立成主形态），留到以后按需加。

## 三、数据形状：给软件侧的 **契约加法草案**

> ⚠️ 这一节可以直接转给 `D:\proj_media` 的会话。**变更性质见 §四。**

### 3.1 推荐形状（改动最小）：沿用 `parentId`，**撤销"两层封顶"**

```jsonc
// brand.json（通用库）—— 与现在完全同源，只是允许更深的链
{
  "contract": "vellum-link/1",
  "scope": "brand",
  "revision": 12,
  "groups": [
    { "id": 10, "name": "品牌视觉", "parentId": null, "sortOrder": 0, "assets": [] },
    { "id": 11, "name": "Logo",     "parentId": 10,   "sortOrder": 0, "assets": [] },
    { "id": 12, "name": "基准式样", "parentId": 11,   "sortOrder": 0, "assets": [ /* asset 同 §5.4 */ ] },
    { "id": 13, "name": "反白版",   "parentId": 11,   "sortOrder": 1, "assets": [] }
  ]
}
```

**对契约 §5.3 的修改（三项）**：

| # | 现在写的 | 改成 |
|---|---|---|
| 1 | 「分组支持**两层**（父组 → 子组）」 | 分组**不限层数**，靠 `parentId` 串成链；**建议上限 5 层**（见 3.2） |
| 2 | 「软件侧**两层封顶**，不会产出三层以上」 | **撤销该承诺**（改为"层数 ≤ 5"） |
| 3 | （未明确写）`assets` 能否挂非叶子组 | **明确：可以挂任意一层**（现状已是如此，只是没写进契约） |

**为什么推荐它**：软件侧本来就用 `parentId` 建树（只差一层限制），**改动最小**；
且 `id` 比路径串更稳（改名不影响树形，不会出现"路径改了、子组没跟上"）。

### 3.2 四条必须写进契约的约束

| 约束 | 值 | 谁拦 |
|---|---|---|
| **深度上限** | **≤ 5 层**（含顶层） | 两侧都拦：软件侧不产出；插件侧**超限当顶层，绝不丢素材** |
| **同级排序** | 同层内按 `sortOrder` 升序，缺失按 `id` | 插件已按此实现（`sortByOrder`）；软件侧保证同层唯一更好 |
| **容错** | `parentId` 缺失 / `null` / 空串 / 指向不存在的组 / **成环** → **一律当顶层** | **插件已实现并保留**（"丢素材比顺序难看严重得多"） |
| **计数口径** | 父组 `count`（若给）= **含所有后代** | 插件侧按此显示；否则只算直属 |

### 3.3 备选形状（插件侧**也能适配**，但需要软件侧明确选一个）

```jsonc
// 备选：扁平 + 显式路径（每个组自带完整路径）
{ "id": 12, "name": "基准式样", "path": ["品牌视觉", "Logo", "基准式样"], "assets": [...] }
```

- 优点：插件侧解析最简单（不建树、不查父）。插件内部**本来就是路径数组**（`groupPath`/`crumb`）。
- 缺点：**改名要批量改所有后代的 path**；软件侧维护成本更高。
- ⇒ **不推荐**，但如果软件侧的存储本来就是"路径 + 分隔符"那种结构，选它也行（**告诉我一声即可**）。
- 两种形状插件侧都能吃：**内部统一成 `path: string[]`**，入口各写一个适配。

### 3.4 插件侧**不需要**新字段

- 不需要 `depth`（插件自己数得出来）；
- 不需要 `fullPath` 字符串（面包屑用数组拼）；
- 不需要新的 scope / 新的文件 —— **同一份 `groups[]`，只是深一点**。

## 四、变更性质：**不升版本**，但它不是"加法"，而是 §十 里没有的一类

**结论：`contract` 保持 `vellum-link/1`，不升 `2`。但归类不是"加法"，而是「约束放宽」。**

### 4.1 判据（硬标准，不靠感觉）

不是看"加字段还是改字段"，而是看**旧客户端拿到新数据会怎样**：

| 旧客户端（v0.9.x）遇到三层数据 | 结果 |
|---|---|
| 崩 / 报错 | ✗ 不会 |
| 丢素材 | ✗ 不会（兜底把它当顶层吐出） |
| 看错层级（**降级显示**） | **✓ 会** —— 第 3 层与父组平级出现在最外层 |

⇒ 三条里两条过关，第三条第可接受（**降级而非损坏**）⇒ **不升版本成立。**

对比"破坏性"长什么样：假如改 `parentId` 的**含义**（比如解释成"父组路径"），旧客户端会把所有组当顶层 —— 那是语义改了，必须升版本。**这次字段含义一个字没动。**

### 4.2 为什么"绝不轻易升版本"（很硬的一条）

按 §十：**升 `vellum-link/2` 要求两侧「必须同步升级」才能用新契约**。
而插件是靠用户**手动装 `.ccx`** 的 —— 无法保证全员同时升级 ⇒ **升版本实际上会把整条链锁死**。
⇒ 凡是"降级能解决"的，**一律不升版本**。

### 4.3 §十 缺一类：建议补一行

现在 §十 只有两类（加法 / 破坏性），**"放宽取值约束"没有归类** ⇒ 将来每次放宽都要重吵一次。
建议在 §十 的表格里补：

| 变更类型 | 处理 |
|---|---|
| **约束放宽**（放宽取值上限 / 枚举范围，旧客户端可**降级**处理） | **不升版本**，但**必须同时写明旧客户端的降级规则**，两侧各自 `DECISIONS.md` 记一条 |

### 4.4 更要紧：**降级规则要写进契约 §5.3**（否则是"未定义行为"）

> 客户端**允许**把"超出其支持深度的组"降级为顶层显示（**不丢素材**）；这**不算错误**。

不写进契约，会出两个问题：
1. 旧插件把三层平掉，**算 bug 还是合规**没有依据，将来会互相甩锅；
2. 将来有人看到"层级平了"，会去查镜像是不是写错了 —— **排查方向被带偏**（这种坑本项目已经踩过）。

### 4.5 三处改动点（契约里"两层"只出现在 **2 行**，都在同一段注里）

实测定位：`LINK-CONTRACT.md` L259 与 L261（**同一个注**）。所以"§2~§8 全改"其实**不必**：

| 位置 | 改什么 |
|---|---|
| **§5.3 那个注（L259-261）** | 两层 → **≤5 层**；删掉"软件侧两层封顶"；补**降级规则**；补四条约束（深度/排序/容错/`assets` 可挂任意层） |
| **§十 表格** | 补「约束放宽」一行（见 4.3） |
| **§5.1（可选，属加法）** | 若同时要落 `tpl` scope，一并写（`docs/53` 已有草案） |
| 其余 §2/§3/§4/§6/§7/§8 | **本轮不需要动** —— 改动面越小，联调风险越小 |

### 🔴 一个必须提前处理的时序问题

**如果软件侧先上线多层、插件侧还是旧版** ⇒ 插件会把第 3 层**压平成顶层**：
用户会看到"基准式样""反白版"**直接出现在最外层**，而且**和父组平级** —— 不丢素材，但**看起来很乱、像 bug**。

🔴 **而且这个顺序没有替代方案**：契约 §六 的 `req.json` 里只有
`contract` / `reqId` / `assetId` / `scope` / `at` —— **没有"插件版本"字段**，反向也没有别的通道
⇒ **软件侧无法得知对方是哪个插件版本**，所以做不到"按版本决定写不写多层"。

⇒ **唯一可行顺序**：

1. **插件侧先做**「能读任意层」的兼容改动 —— 对**现在这份两层数据行为完全不变**（可安全先发）；
2. 软件侧再放开多层产出；
3. 两侧各自公告后，插件侧再上"面包屑下钻"的 UI 形态。

⇒ 推论：**多层数据在旧插件上降级会是"常态"**（同事装插件靠手动），必须接受 —— 这也是 4.4 那条降级规则非写不可的原因。

## 九、方案 B 的高度预算（2026-10-17 用户提问驱动）

> 用户问：「这个目录面板加上插入面板，瀑布流会不会就没地方了？」
> **会 —— 但只在"子目录做成固定占位"这一种做法下会。** 这一问逼出了一条必须在实现前定死的约束。

### 9.1 现有各块的高度（取自 `index.html` 的真实 CSS）

| 块 | 高 | 说明 |
|---|---|---|
| `.lib-top`（库 tabs + 刷新） | **34** | |
| `.lib-meta`（契约 / 生成时间） | **27** | 排障用，**可收进 tooltip** |
| `.lib-bar`（两行 chips） | **60** | 只能表达两级 —— 正是要换掉的东西 |
| `.lib-foot`（**插入面板**） | **30 / 150** | 未选中一行提示；选中展开。**位置在网格上方**（v0.3.2 用户明确要求） |
| ↳ 其中落点九宫格 | **66** | 3 列 × 3 行，宽 96px |
| 网格 `.lib-body` | **429 / 309** | 580 − 上面各项（未选中 / 选中） |

### 9.2 四种做法的网格可用高度

| # | 做法 | 未选中 | 选中一个素材 |
|---|---|---|---|
| ① | 现状（两行 chips，无面包屑） | **429** | 309 |
| ② | B + 子目录**固定占位**（3 个子目录） | **348** | **228** |
| ③ | B + 子目录**并进滚动区** + 撤 chips | **459** | **339** |
| ④ | ③ 再把九宫格收成「落点：居中 ▾」下拉 | 459 | 383 |

> ⚠️ ② 真正的问题**不是"3 个子目录"**，而是**子目录数量不可控**（软件侧说了算）：
> **10 个子目录 = 320px，网格直接消失**。⇒ 这条路不能用。

### 9.3 结论（实现时必须守的 5 条）

1. **子目录区必须在滚动区（`.lib-body`）内**，不能 `flex: 0 0 auto` 固定在网格之上；
2. **撤掉两行 chips（−60）**、换成**一行面包屑（+30）** ⇒ **净赚 30px**，且层数不再受限于 2；
3. **面包屑固定在顶部**（不能滚走，否则用户在深目录里会迷路）；
4. 子目录超过 4 个时折叠成「还有 N 个子目录」（可选，防止一进层全是文件夹、看不到文件）；
5. **叶子层（无子目录）与现在完全一致**，只是 chips 换成面包屑 ⇒ 这条最容易被忽略，但它决定了"绝大多数时候不变化"。

**可选优化（待用户定）**：九宫格收成一行「落点：居中 ▾」下拉 ⇒ 选中时再多 44px。
代价是"点两下才能改落点"，而落点是**每次插入前都要确认**的高频操作，不一定划算。

图：`preview/b-height-budget.png`（四屏对比 + 高度堆叠条）。

### 12.2 🔴 用户截图报障：文字与按钮「贴边甚至溢出」

**根因**：`.lib-foot` 有 `border` + `background`，是张"卡片"，但水平内边距写成了 **0**
（`padding: 8px 0`）⇒ 文字贴左边框、按钮贴右边框。
外层 `.s-lib` 的 `padding: 12px 14px 0` 是卡片**外面**的留白，管不到卡片内部 ——
所以"外面明明有 14px"和"里面贴边"可以同时成立。

**修法**：`padding: 8px 10px`（只动水平方向，垂直不动）。
真机读数：**左 11px / 右 11px**（10 + 1 边框）；高度 **52 → 53px**，仍在 40–56 判据内。

### 12.3 🔴 为什么 S71 之前没抓到（判据的盲区）

⇒ 补第 5 条**几何判据**：「内容块左沿 − 卡片左沿 ≥ 8px」，并用 `getBoundingClientRect` 量，
**不解析 CSS 字符串** —— 样式怎么写都无所谓，**看得见的留白**才是判据。
