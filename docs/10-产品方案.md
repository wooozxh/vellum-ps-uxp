## 一、需求

### 1.1 一句话

给公司设计部门做一个 Photoshop UXP 插件，形态是**工具合集**：一个入口界面，里面装若干互不干扰的小工具，逐个补齐。

### 1.2 子功能清单与优先级

| # | 工具            | 做什么                             | 里程碑        |
| - | ------------- | ------------------------------- | ---------- |
| 1 | **调色板**       | 品牌预设色 + 自定义常用色；点击设为前景色 / 背景色    | **M1（本轮）** |
| 2 | **素材 / 样机库**  | 浏览本地文件夹里的素材 / 样机，点预览图把素材插入画布    | M2         |
| 3 | **表格工具**      | 导入 Excel，把表格重绘到画布（文字 + 矢量，可再编辑） | M3         |
| 4 | 其他（AI 控 PS 等） | 先留位，以后再说                        | 后续         |

### 1.3 非目标（本阶段明确不做）

- **不引入前端框架、不引入构建链** —— 用户已选 vanilla，理由是保住「改码 → load → 读结果」这条闭环的速度。
- 表格首版**不做**：合并单元格、公式、富文本、对已生成表格的「原地刷新」。
- 素材首版**不做**「智能对象替换」式样机（先做"把素材直接置入画布"）。
- 不做多语言（界面中文即可）。

**脚注（两处相对原拟稿的调整）**

### 2.3 注册表机制（架构核心）

每个工具是一个**独立模块**，导出统一描述符：

```js
// tools/palette.js（示意）
module.exports = {
  id: "palette",
  title: "调色板",
  subtitle: "品牌色 / 我的颜色",
  mount(container, ctx) { /* 把自己的界面画进 container */ },
  unmount() { /* 清理事件、停止计时器等 */ }
};
```

外壳只做三件事：**读注册表 → 渲染首页 → 点击时 mount / 返回时 unmount**。

**收益**：加第 5、6 个工具 = 新增一个文件 + 注册表加一行，**外壳零改动**。  
所有工具共用 `lib/` 三个底座：日志通道、PS 操作封装、数据存储。

## 三、界面与交互

### 3.1 外壳（首页）

PS 面板通常**窄而高**（停靠时约 280–360px 宽），所以采&#x7528;**「宫格首页 → 进工具 → 返回」的下钻式**导航，而不是「左列表 + 右内容」（右侧内容区会被挤没）。

```
┌── Vellum 工具箱 ─────────────┐
│                              │
│  ┌────────┐   ┌────────┐    │
│  │ 调色板 │   │ 素材库 │    │   ← 首页：工具宫格
│  │ 品牌色 │   │ 插入   │    │
│  └────────┘   └────────┘    │
│  ┌────────┐   ┌────────┐    │
│  │ 表格   │   │ (预留) │    │
│  │ Excel  │   │        │    │
│  └────────┘   └────────┘    │
│                              │
│  状态：就绪                   │   ← 状态条（与 boot.log 对应）
└──────────────────────────────┘

点「调色板」后：

┌── ← 调色板 ──────────────────┐
│  品牌色                      │
│  ■ ■ ■ ■ ■ ■                 │   ← 点击 = 设前景色
│  我的颜色            [+ 存当前]│
│  ■ ■ ■ ■ ■                   │   ← 点击 = 设前景色；长按/右键 = 删
│                              │
│  左键=前景色  Shift+左键=背景色│   ← 操作提示（待确认，见第九节）
└──────────────────────────────┘
```

### 3.2 调色板（M1）

**界面元素**

- **品牌色区**：公司品牌标识色，一组固定色块（来源见下）。
- **「我的颜色」区**：用户自行存储的常用色；含「＋ 存为我的颜色」按钮（把当前前景色存进来）。
- **底部提示行**：说明左键 / 修饰键的作用。

**操作步骤**

1. 打开面板 → 点「调色板」→ 进入。
2. 点任意色块 → 设为**前景色**；`Shift+点击`（或右键，待确认）→ 设为**背景色**。
3. 点「＋ 存为我的颜色」→ 把当前前景色追加到「我的颜色」，落盘。
4. 长按 / 右键某个「我的颜色」色块 → 删除（待确认交互）。

**品牌色来源（拟）**：插件内自带一份默认 `palette.json`（品牌色预置）；`PluginData` 里的用户数据覆盖/追加自定义色。  
→ **待你提供**：品牌标识色的具体色值（HEX），或先给几个占位色。

### 3.3 素材 / 样机库（M2，本轮只立框架不实现）

> ⚠️ **2026-10-10 需求变更**：本工具改为「与 VellumDesk 联动」，**不再由插件自己扫文件夹**。详见**第十节**。

- 顶部：目录选择 + 刷新。
- 主体：缩略图列表 / 网格，点一下 → 把素材作为新图层**置入**当前文档。
- 样机：后续再做「替换智能对象内容」式样机。

### 3.4 表格工具（M3，本轮只立框架不实现）

- 选文件 → 解析 `.xlsx` / `.csv` → 预览 → 设参数（字号、行高列宽、描边、底色）→ **一键重绘到画布**。
- 重绘形态 = **文字图层（每格一个）+ 矢量线条**，插入后可在 PS 里继续改字改色。
- 「方便调整」的定义待你明确（见第九节），首版倾向：**导入前设参数 + 插入后手动微调**。

## 四、边界情况（必须处理的）

| 场景                   | 处理                                                                  |
| -------------------- | ------------------------------------------------------------------- |
| **没有打开任何文档**         | 调色板**照常可用**（前景/背景色是应用级的，不依赖文档）；素材插入与表格重绘**给出明确提示**并阻止（或询问是否新建画布，待定） |
| 设前景/背景色失败            | 捕获异常，写 `boot.log`（`FAILED <原因>`），状态条显示失败，不静默                        |
| 「我的颜色」为空             | 显示空态提示，不报错                                                          |
| 颜色超出色域 / 文档是 CMYK、灰度 | 统一按 **RGB** 设置，让 PS 自己转换；不做色域告警（首版）                                 |
| 素材目录被删 / 无权限         | 给出提示，保留已加载列表，不崩溃                                                    |
| 表格超大（几百行）            | 建几百个图层会拖慢 PS；首版对行×列设**上限并在超限时明确警告**                                 |
| 面板被重复打开 / 重复 mount   | `unmount` 必须解绑事件，避免监听器叠加                                            |

## 五、技术方案（关键技术点 + 待实测清单）

### 5.1 复用 `hello-world` 已验证的骨架

- manifest v5：`host` 是数组；权限**按需显式声明**。
- 修改文档一律包在 `core.executeAsModal()` 内。
- 建文字图层走 **DOM** `app.activeDocument.createTextLayer({contents})`，**不用** batchPlay 的 `make+textKey`（`docs/04` 的硬结论）。
- 反馈走**文件**：`appendLog` 写 `PluginData/boot.log`。

### 5.2 本轮要新增/实测的技术点

| 技术点                | 用途         | 状态                                                                                                                    |
| ------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------- |
| **设置前景 / 背景色**     | 调色板核心      | ✅ **实测已通过**（2026-10-10）：`set {_target:[{_ref:"color",_property:"foregroundColor"}], to:{_obj:"RGBColor",red,grain,blue}}`。⚠️ **读与设的 `_target` 写法不同，用错会静默失败**；绿色键名是 `grain`。见 `lib/ps.js` 文件头 |
| 读取当前前景色            | 「存为我的颜色」   | ✅ **实测已通过**：`get {_target:[{_property:"foregroundColor"},{_ref:"application",_enum:"ordinal",_value:"targetEnum"}]}` |
| PluginData JSON 读写 | 存自定义色      | ✅ 目录可写（`getDataFolder` 已证可写）；M1 已实装并验证跨重载持久化                                            |
| 本地文件夹读取 + 缩略图      | 素材库        | ⛔ 待实测：目录授权 token、本地图片能否在面板内显示（`file://` 已证**被拒**，故联动改走镜像）                     |
| 置入文件为新图层           | 素材库        | ⛔ 待实测                                                                                                                 |
| xlsx 解析            | 表格工具       | ⛔ 待实测：**免构建**方案（vendored SheetJS UMD）是否能在 UXP 里跑                                                                      |
| Command 打开面板       | Command 定位 | ⛔ 未验证。UXP 未提供「唤起面板」的 API，故 M1 的 Command 一律走**纯动作**（设色），不依赖面板 —— 这是安全设计                          |

> 原则：**拿不准就实测，不猜**。每个 ⛔ 项在对应里程碑开工前，先写小探针在真机验证，结论回写本文档与 `DECISIONS.md`。

### 5.3 数据存储

- 位置：`PluginData`（`getDataFolder()`），**不是**插件目录（插件目录只读，见 `DECISIONS.md`）。
- 文件：`palette.json`（品牌色覆盖 + 我的颜色数组）。
- 读取失败/文件不存在 → 用内置默认值，不报错。

**M1 期间修掉的两个真 bug（都是自检抓出来的，不是事后发现的）**
1. **品牌色网格从未渲染** —— `build()` 只建容器没填内容，面板里两个网格都是空的。自检 S1 一眼抓出。
2. **落盘判据假阳性** —— 只按颜色值匹配，会等到上一次遗留的旧条目，于是"点击没生效"也能判 PASS。改为必须匹配**本次新增的 id**。

**三条新增的实测结论（已进 `DECISIONS.md`）**
- UXP 的 `new MouseEvent("click", {shiftKey:true})` **构造不报错但会丢掉 `shiftKey`** → 带修饰键的合成点击会静默退化成普通点击。正解：造普通 `Event` 再把 `shiftKey` 当**自有属性**挂上去。
- `executeAsModal` 与轮询读取可以并存（自检在设色后立刻轮询回读，未出现模态争用）。
- **Command 无法唤起面板** → 命令一律设计为纯动作。

**唯一无法自证的一项**：面板的**视觉呈现**（布局好不好看、挤不挤）。AI 点不了 PS 的菜单，所以「窗口 > 插件 > Vellum 工具箱」这一步需要人工看一眼 —— 这是物理上没法代劳的部分。

## 十、与 VellumDesk 联动（2026-10-10 新增需求 · 设计待确认）

**需求（用户原话）**：希望这个插件能和另一个产品 **VellumDesk** 联动 —— 在 VellumDesk 里统一管理素材/目录，**实时推送到插件并更新**。

**VellumDesk 是什么（已核查 `D:\proj_media`）**：Electron + React/TS + SQLite(better-sqlite3) + sharp/FFmpeg 的本地素材管理桌面软件（对外名「Vellum工作台」，appId `com.vellumdesk`，当前 v1.9.6）。  
素材实体在工作区 `D:\vellum_workspace`（三级：工作区/项目/任务包，含版本 `V1…` 与三组），库元数据在 SQLite，缩略图在 `_thumbs`。

**⚠️ 关键事实：它没有对外接口。** 全库 grep `createServer` / `WebSocket` / `.listen(` / `express` **零命中**；renderer↔main 走 IPC，纯本地不上云。  
→ 因此**联动不可能只改插件一侧**，无论哪条路线都要动 VellumDesk 本体，而它是**另一个项目**（有自己独立的档案与铁律）。本联动须**两边分别立方案**。

### 10.1 三条路线（成本 vs 能力）

| 路线           | VellumDesk 侧改动         | 实时性     | 能拿到                         | 代价                              |
| ------------ | ---------------------- | ------- | --------------------------- | ------------------------------- |
| **A 直读工作区**  | **零改动**                | 轮询（准实时） | 项目/任务/版本/文件 + `_thumbs` 缩略图 | 拿不到标签/检索（在 SQLite）；UXP 读 D 盘需授权 |
| **B 导出快照**   | 小（变更时写 `library.json`） | 轮询      | A + 标签/类别等元数据               | 仍非真推送；需约定快照格式                   |
| **C 本地联动服务** | 中（HTTP + WebSocket 常驻） | **真推送** | 全部 + 缩略图/原图走 HTTP + 可双向扩展   | 要在 VellumDesk 加服务与依赖；改动最多       |

**倾向：C**（用户要的就是"实时推送"；且 HTTP 可绕开 UXP 本地目录授权的麻烦）。A/B 作为"先轻后重"的过渡选项保留。

> ⚠️ **此倾向已被 10.5 修正**（2026-10-10 复评）：用户质疑"都能读对方文件夹就不必用 HTTP"，复评后确认 HTTP **非必需**，改为「先 ②（镜像单写，无服务）后 ③（本地服务）」。详见 10.5。

### 10.2 探针实测结论（2026-10-10，已跑通）

探针：`link-probe/`（插件）+ `tools/linkprobe/server.mjs`（配套本地服务，零依赖）。**实测矩阵 5/6：**

| 能力                                 | 结果 | 证据                       |
| ---------------------------------- | -- | ------------------------ |
| `fetch` 本地 HTTP JSON               | ✅  | `status=200 items=3`     |
| `<img>` 直连 HTTP 图片                 | ✅  | `naturalWidth/Height=96` |
| `fetch`→`blob`→`objectURL`→`<img>` | ✅  | `blob=19485B → 96×96`    |
| `WebSocket` 收本地服务**主动推送**          | ✅  | 收到 `library-changed` 事件  |
| 本地磁盘 `file://` 图片                  | ❌  | `onerror`（被拒）            |

**结论：路线 C 的三项核心能力（拉数据 / 拉缩略图 / 收实时推送）全部成立 → C 可行且推荐。**

两个必须记住的坑（详见 `link-probe/README.md`）：

1. **`display:none` 容器里 UXP 不加载图片** —— 表现是"超时"，极易误判成"网络被拒"；承载图片的 DOM 必须**可见**。
2. **`network.domains` 写 localhost / IP 一律不匹配**（Adobe 已知缺陷，UXP 9.0.2 实测），  
   **只能写字符串 `"all"`** —— 代价是插件获得"访问任意域名"的权限；对内网工具可接受，但需知悉。

另：`file://` 被确证拒绝，故路线 A/B「插件直读磁盘显示缩略图」不能直接用 `file://`；  
理论上可绕道「UXP storage 读文件 → Blob → objectURL」（objectURL 已证可用），但**该环尚未实测**。

### 10.5 复评：为什么「不一定需要 HTTP」（2026-10-10，用户质疑）

**用户质疑**：既然插件和 VellumDesk 都能读对方的库文件夹，为什么还要 HTTP？

**复评结论：成立 —— HTTP 非必需。** 此前把「要实时推送」直接等同于「必须起服务」，是**过度设计**。

**关键事实：读盘能力不对称（决定「能不能读」的是读它的程序，不是文件夹）**

| 读取方                  | VellumDesk 工作区 | 插件 PluginData |
| -------------------- | -------------- | ------------- |
| VellumDesk（Electron） | 可读（全盘）         | **可读（全盘）**    |
| PS 插件（UXP）           | **受限 / 未知**    | 可读（自身沙箱，已证）   |

→ 「共享文件夹」这个想法要成立，必须解决「插件读 VellumDesk 目录」这**唯一一个问号**，或**把它绕开**。

**两问拆解**（HTTP 只回答了第 2 问，第 1 问它没管）：

1. 数据归谁、谁写谁读（**存储拓扑**）；


1. 变更怎么通知 + 图片字节怎么到渲染层（**传输 / 事件**）。第 2 问也有**不需要 HTTP** 的解：  
   插件读**自己的目录** + 图片走 `data:` URL（**均已实测通过**）。

**三条路线（修正版）**

| 路线               | 谁写、写到哪                         | 插件读什么                 | 实时机制    | 插件侧改动       | 软件侧改动        | 已知风险                                       |
| ---------------- | ------------------------------ | --------------------- | ------- | ----------- | ------------ | ------------------------------------------ |
| ① 插件直读工作区        | 不写（VellumDesk 本就写）             | `D:\vellum_workspace` | 轮询目录    | 需 UXP 目录授权  | **零**        | 授权链路脆弱；拿不到 SQLite 标签；本地图渲染未证；`file://` 已被拒 |
| **② 镜像单写（已选定）** | **VellumDesk 写进插件 PluginData** | **自己的目录（保证可读）**       | 轮询自己的清单 | 小           | 中（监视 + 写镜像）  | PluginData 路径含 PS 版本号，需动态发现；**非真推送**       |
| ③ 本地服务 HTTP+WS   | VellumDesk 起服务                 | 网络                    | **真推送** | 小（fetch/WS） | 大（常驻服务 + 依赖） | 插件获 `"all"` 网络权限                           |

**提议：先做 ②，把「数据契约」定死；日后确需毫秒级推送再升 ③（同一份契约，只换传输层）。**  
理由：② 只用**已实测通过**的能力（读自身目录 + `data:` URL 图片）；不引入网络权限；改动集中在「本就该改」的  
VellumDesk 侧；符合项目「先轻后重」。**✅ 已拍板（2026-10-10，用户确认 ②；③ 正式放弃）。**

**② 的前置待实测 —— ✅ 已实测（2026-10-10，自检 S19，详见 `docs/11` §一）**：

- **「读自身文件」这一环成立**：`storage.localFileSystem.getDataFolder()` → `getEntry` 逐级进子目录
  → `read({format: formats.binary})` 拿到**真二进制**（实测字节数与磁盘一致 = 4814B，
  文件头魔数 `RIFF` 正确 —— 这排除了"被按文本解码"）。
- **但渲染有一个平台坑**：UXP 的 `<img>` **不解码 webp** → 缩略图必须 png/jpg（见 §10.6 的更正）。
- 仍待办：VellumDesk 侧如何**稳定定位** PluginData 路径（随 PS 版本号变化）。

### 10.6 镜像「写什么」与性能预算（2026-10-10 实测）

**用户追问**：软件库文件很多时，是每个文件都写一遍吗？会不会性能很差？

**答：只写「清单 + 缩略图」，原图一个都不搬**（除用户点「插入」的那一刻，按需取那一张）。

镜像目录（落在插件 PluginData 内，插件保证可读）：

```
PluginData/library/
├── manifest.json        ← 清单（小）：每项 = id / 名称 / 标签 / 尺寸 / 缩略图文件名 / 原图路径(字符串) / 代次 gen
├── thumb/<id>.webp      ← 缩略图（唯一被搬运的"图片文件"）
└── handoff/             ← 按需：点"插入"时，VellumDesk 才把这一张原图拷进来
```

三条关键设计：
1. **原图不镜像** —— 原图只在 manifest 里留一个**路径字符串**，供「插入」时定位；插入时按需取一张。
2. ~~**缩略图直接复用 VellumDesk 的 `_thumbs`**（它已生成好，webp），不重新生成。~~
   → **⚠️ 2026-10-10 实测推翻：UXP 的 `<img>` 不解码 webp。**
   真机矩阵（render 到 `opacity:1` 的可见容器，`naturalWidth` 判据）：
   `webp-alpha`（VP8X 带 alpha）✗　`webp-plain`（VP8 有损）✗　`png` ✓　`jpg` ✓
   —— 两种 webp 编码变体、data URL 与 blob URL 两条路**全失败**，同容器里 PNG/JPEG 正常。
   ⇒ **镜像里的缩略图必须是 png 或 jpg**，VellumDesk 侧写镜像时要转码。
   ⇒ 连带影响 §10.6 的**体积预算**（见下方更正）。详见 `docs/11-素材库联动方案.md` §一。
3. **增量同步** —— manifest 带 `gen` 代次；VellumDesk 记住上次写到哪，只写变化项；插件轮询只 `stat` 一个 `manifest.json`。

**实测数据（本机 SSD）**

当前库体量：**工作区总量 127 MB，而缩略图总共只有 48 KB**（7 张 webp，平均 **4.2 KB/张**）。
→ 镜像若连原图一起搬，每次变更可能搬几十 MB；**只搬缩略图则小 3 个数量级**。

写入/读取大量 8 KB 小文件的压测：

| 素材数 N | 缩略图总量 | 首次全量写入 | 读回全部 | stat 全部 |
| --- | --- | --- | --- | --- |
| 200 | 1.6 MB | 155 ms | 77 ms | 3 ms |
| 1,000 | 7.8 MB | 711 ms | 378 ms | 12 ms |
| 3,000 | 23.4 MB | **2,124 ms** | 1,145 ms | 36 ms |

**结论**：即便 3000 个素材，**首次同步约 2 秒**；此后走增量，通常只动 1 张图 + 重写 manifest。
轮询只 `stat` **一个**文件（36 ms 是 stat 3000 个的开销，实际只 stat 1 个 → **<1 ms**），开销可忽略。
**性能不是 ② 的问题。**

**② 的三个代价（知悉即可）**：
① 「插入原图」需一次**文件握手**（插件写请求 → VellumDesk 放 1 张原图 → 插件置入），比 HTTP 多几十~几百 ms；
② 非毫秒级推送（轮询秒级）；③ PluginData 路径含 PS 版本号（`PHSP\27\`），VellumDesk 需动态发现。

### 10.7 镜像的「结构」：项目 / 任务 / 稿 / 三组 + 通用库（2026-10-10）

**用户追问**：软件里任务多、素材多，且分「成品图 / 素材图 / PS 工程」；插件这边也要能按**同样的结构**访问；
另外软件侧要新建一个**独立于任务的通用库**（公司品牌识别素材），插件也要拿到。

**答：能，而且「结构」是白送的 —— 结构就是数据，JSON 想嵌套几层都行。**

**已核实的 VellumDesk 数据结构**（`D:\proj_media\src\main\db.ts` / `workspace.ts`）：

| 层 | 表 / 常量 | 关键字段 |
| --- | --- | --- |
| 项目 | `projects` | id / name / color / sort_order / archived |
| 任务包 | `packs` | id / name / category / channel / folder_path |
| 稿（版本） | `pack_versions` | `seq`（V1/V2…）/ folder_name / is_current / delivered_at |
| 角色分类 | `assets.role` | **`成品` / `素材` / `工程` / `未归属`** —— 由所在子文件夹决定（`01-成品` `02-素材` `03-工程`），**不猜后缀** |
| 标签 | `tags` + `asset_tags` | dimension / name / color，多对多 |

**映射（不新增概念，直接照搬）**：
`projects[].packs[].versions[].files[]`，每个 file 带 `role` / `ext` / `name` / `thumb` / `absPath`（**字符串**）/ `tags[]`。

**缩略图覆盖是全的（好消息）** —— 查 `src/main/thumbs.ts`：
图片走 sharp、视频走 FFmpeg 抽帧、**PSD / PSB 走内嵌合成预览 JPG**、PDF 走 pdfjs 首页。
`THUMB_SIZE = 320`、webp q78–82。→ **PS 工程文件也有预览图**，插件里不会是空白格。

**「插入」按类型分派（所以 manifest 必须带 `ext` / `kind`）**：

| 类型 | 插件里点一下 |
| --- | --- |
| 位图 jpg/png/webp/gif… | 置入为新图层 |

| PDF | 视 PS 能否置入而定，M2 探针 |

**通用库（品牌识别素材）**：建议**单独一份 `brand.json` + `brand/thumb/`**，与任务库分开。
理由：品牌库小、稳定、变动少；任务库大、churn 高 —— 分开 = 分开同步节奏，品牌库几乎不用重传。

> ⚠️ **前置事实**：通用库这个「**独立于任务的库**」在 VellumDesk **目前并不存在** ——
> 现有模型里 `assets` 只能挂在 `packs` 上（可 NULL = 未归属）。故它是 **VellumDesk 侧的新功能**，
> 须在那边先立方案。本插件侧**先在 manifest schema 预留 `scope: "brand" | "task"`**，不受影响。

**续航提示（可选优化）**：`manifest` 全量（结构 + 元数据，几百 KB 级）+ **缩略图按需** ——
复用同一个「请求文件」通道，插件打开某任务时才请 VellumDesk 补该任务的缩略图，首同步可做到瞬时。
