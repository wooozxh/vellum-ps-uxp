## 二、反馈 1 · 悬停闪烁 —— 归因与修法

### 2.1 旧写法（v0.2.1）

每个色块**各自**绑一对事件：

```js
binder.on(sw, "mouseover", (ev) => { sw.classList.add("is-ho"); showTip(wrap, tip, sw, hex, name); });
binder.on(sw, "mouseout",  () => { sw.classList.remove("is-ho"); hideTip(tip); });
```

### 2.2 两条致命伤（叠在一起才"疯狂"）

**伤① mouseover/mouseout 会成对触发。**
指针在「色块 ↔ 它的子元素」之间移动时，父节点会收到 `mouseout`。
色块的子元素有两个：`.sw-ring`（绝对定位、铺满整块的描边环）和 `.sw-del`（删除叉）。
→ 只要指针跨过这些边界，`mouseover`/`mouseout` 就成对刷 → `hideTip`/`showTip` 高频交替。

**伤② 浮层压在色块上，形成振荡回路。**
旧版纵向定位是 `top = max(0, 色块top - 浮层高 - 5)`：
第一行色块的浮层算出来是负数 → 被 clamp 到 **0** → **浮层正好盖在色块自己身上**。

于是最坏情况是这样一圈：

```
指针在色块上 → 浮层压住指针
   ↑                    ↓
色块重新获得 hover ← 浮层消失（mouseout）← 指针落到浮层上（色块失焦）
```

**这是"疯狂"的来源** —— 稳定态不是"显示"或"隐藏"，而是"以帧率抖动"。
（`pointer-events:none` 理论上能挡住这条路，但 UXP 是否兑现这条属性我们**没有验证**，所以不能把它当护栏。）

### 2.3 判别证据（真机）

新增 **S15**，测的不是"看起来对不对"，而是一条**几何不变量**：*浮层矩形不得与任何色块矩形相交*。

```
S15 PASS  同步量=0x0　让帧后首行=155x25 相交色块=0
          让帧后末行=130x25 相交色块=0　落在网格外=true/true
```

- `同步量=0x0`：浮层刚从 `display:none` 变可见的**同一同步块**里量不到尺寸
  → 这正是旧版定位算错、然后被下一次 mouseover 重算一次的物理原因
  （又一次印证 v0.2.1 那条结论：**UXP 布局是异步的**）。
- `相交色块=0`：**振荡回路在物理上不成立**了 —— 指针在网格内移动时，它下方永远不可能是浮层。

### 2.4 修法 —— 四条纪律（写进 `tools/palette.js` 文件头，改动前必读）

| # | 纪律 | 落点 |
|---|---|---|
| ① | **单一活动源**：只有 `mouseover` 能改"当前悬停色块"；**色块自己不绑 mouseout** | `makeSwatch` 只绑 mouseover；`bindRootHover` 在根节点正着判"指针还在不在活动色块内部"（`insideSwatch` 走 parentNode，不用 `contains`） |
| ② | **幂等**：活动色块没变就一个字节都不写 | `activateTip` 首行 `if (hov && hov.el === sw) return;`；`setRoHex` 值相同则不写 |
| ③ | **浮层永不覆盖色块**：纵向一律落在 `.sw-grid` 之外（色块在网格上半→浮层在上方，下半→下方） | `placeTip()` |
| ④ | **让帧后量**：先用估算尺寸立刻摆好（不闪到左上角），再 `await dom.settle()` 用实测尺寸精确校正，并用令牌作废过期校正 | `activateTip()` + `estTipSize()` + `tipToken` |

另外两处：
- **隐藏改为"延时确认 + 可取消"**：`scheduleHide(90ms)`，任何一次色块激活都会取消它
  → 即使在某些 UXP 实现里 `relatedTarget` 恒为空（每次 mouseout 都排一次隐藏），
  紧随的 mouseover 也会取消，而且重复激活是幂等的 → **仍然不会闪**。这个设计对"宿主行为不确定"是免疫的。
- **删掉色块的 `title` 属性**：我们已有自绘浮层，再挂一个宿主原生 tooltip 就是两个标签叠加，
  且原生那条的重绘时机不受我们控制 —— 它也在"闪烁"的嫌疑名单里。提示文案由下方 `.hints` 承担。

### 2.5 回归守护

| 层 | 判据 |
|---|---|
| 真机 `S15` | 浮层矩形与**任何**色块矩形都不相交 + 落在网格外 + sync/settled 双读数 |
| 离线断言 15 | `tools/palette.js` 里**不允许**再出现 `binder.on(sw, "mouseout"`；且 `bindRootHover`/`insideSwatch` 必须存在 |

一句静态判据挡住"有人把 mouseout 加回去"，一条几何判据挡住"浮层又跑到色块上面去了"。

## 三、反馈 2 · 填充能力（新功能）

### 3.1 交互设计：为什么是 `Alt+左键`

现有语义族是「左键=前景色 / Shift+左键=背景色」。填充需要一个**不冲突且在 PS 里有共识**的修饰键，
`Alt` 是最自然的：**PS 自己的 `Alt+Backspace` 就是"用前景色填充"**，语义不会有人误解。

| 操作 | 行为 |
|---|---|
| 左键 | 设为前景色 |
| Shift+左键 | 设为背景色 |
| **Alt+左键** | **用该色填充当前图层 / 选区（不改前景色、不改背景色）** |
| 右键 / ✕ | 删除（仅「我的颜色」） |

优先级：**Alt > Shift > 无**。

### 3.2 描述符：照抄官方，不加 `_target`

```js
// 路径①：直接指定颜色（默认走这条）
{ _obj:"fill", using:{ _enum:"fillContents", _value:"color" },
  color:{ _obj:"RGBColor", red, grain, blue },
  opacity:{ _unit:"percentUnit", _value:100 },
  mode:{ _enum:"blendMode", _value:"normal" },
  _options:{ dialogOptions:"dontDisplay" } }

// 路径②：官方原样（Adobe 文档与 UXP wiki 都用这条，等价 Alt+Backspace）
{ _obj:"fill", using:{ _enum:"fillContents", _value:"foregroundColor" }, ... }
```

- **不加 `_target`**：Adobe 论坛有实例显示给 `fill` 加 `_target` 后反而失效
  （forums.creativeclouddeveloper.com/t/batchplay-does-not-behave-as-expeted/6310）。
  不加 = 作用于"当前文档的活动图层 + 当前选区"，正是我们要的语义。
- **默认走路径①**：它的好处是**不碰用户的前景/背景色** —— 这正是这个功能的卖点。
  代价是 `fillContents:"color"` 这条枚举值**官方文档没写**，最坏情况是被静默忽略。

### 3.3 判据：不信"命令没报错"，只信像素

`fillLayer(hex, { verify })` 三档：

| verify | 判据 | 用在 |
|---|---|---|
| `pixel` | 像素回读**等于**目标色 | 自检（必须跑在纯色文档上） |
| `change` | 像素回读**有变化**（或已等于目标色） | 用户路径（能识破"静默忽略"） |
| `none` | 命令执行成功即算成功 | 兜底 |

路径①若被静默忽略，会自动换路径②（先设前景色→填充→**还原前景色**），并把两条路径的
结果都记进日志（`attempts=[...]`）。**自愈**，不靠我猜哪个枚举值在哪个版本上有效。

### 3.4 真机结论：`fillContents:"color"` 在 PS 27.2 上**有效**

```
palette fill hex=#E60012 via=alt+click ok=true path=fillColor verify=change
  readback=#E60012 before=#FFFFFF layer="背景" doc="未标题-2" sel=false
  attempts=[fillColor=已执行/像素命中]
```

`before=#FFFFFF → readback=#E60012`：**新建的纯白文档被精确填成了目标色**，
而且走的是路径①（没有动用前景色）。**回退路径不需要。**

### 3.5 边界与失败语义（绝不"点了没反应"）

| 情况 | 行为 |
|---|---|
| 没有打开的文档 | `✗ 填充失败：没有打开的文档（填充需要先打开一个文档并选中图层）` + 明确不动作 |
| 图层类型不支持（文字/调整/锁定） | 两条路径都执行但像素无变化 → `填充命令已执行，但像素未观察到变化 —— 可能是该图层类型不支持填充…` |
| 有选区 | 只填选区；日志与状态栏都带 `sel` / "选区"字样，让用户知道作用范围 |
| 路径②被动用 | 用完**还原前景色**，日志记 `fgRestored` —— "不改我的前景色"这条承诺不能靠运气 |

### 3.6 快捷键的现实（**更正 v0.2.1 的说法**）

v0.2.1 的 `docs/16` 写的是「`manifest v5` 的 `command` 支持 `shortcut`，但必须含 Ctrl…」。
本轮查证后要补上最关键的一半：

- **语法层面**（官方 Premiere UXP manifest 文档，同一套 UXP 内核）：
  `"shortcut": { "mac": "Cmd+Alt+F", "win": "Ctrl+Alt+F" }`
  Mac 必须含 Cmd 或 Ctrl；Win 必须含 Ctrl；**只支持字母/数字**（标点、方向键、F1–F12 都不行）；
  **与宿主内置快捷键冲突会被静默忽略**（只在开发者控制台留一行警告）。
- **但那是 Premiere / InDesign / XD 的文档。**
  Adobe 官方论坛（Photoshop / UXP 分区）从 2021 一直问到 **2024**，答案都是 **"Not yet possible"**；
  Adobe 员工 2024-06 明确说"**UXP 核心 API 不支持键盘快捷键**"，社区给的替代方案是
  「**录成动作再绑 F 键**」。
- 所以本项目里那条 shortcut 是 **best-effort**：语法合规（真机 `Validate command successfull` 通过），
  但**很可能被 PS 直接忽略**。→ 必须人工按一次 `Ctrl+Alt+F` 才知道（见 §五 未自证清单）。
- **真正能自证的是面板内的修饰键**（`Alt+左键`）—— 它走我们自己的事件处理器，
  已经被 S16 端到端验证（`alt 生效=true`）。

## 四、顺带修掉：**探针基座判据自己写错了**（第三次同一家族）

复验 v0.2.2 时发现日志里 5 条**本来正确**的几何结论都被盖了章：

```
cssprobe NO 测量基座自证 :: 容器宽=0px → ⚠️ 基座无效：一切几何结论作废
cssprobe OK CSS 自定义属性 :: 实测宽 137px　⚠️ 基座未参与布局，此结论不可信
```

**矛盾就在于**：同一个容器，`CSS 变量` 探针能量到 137px、`布局测量` 能量到 100px，
只有基座自己报 0。→ 说明"容器不参与布局"是**假**的，量到的其实是
**"首次 append 一整棵子树需要超过 2 帧"**（第一次布局延迟）。

修完之后紧接着又抓到第二个问题（更难）：

```
18:2X 运行 A：CSS 自定义属性 → 实测宽 137px  ✅
18:2X 运行 B：CSS 自定义属性 → 实测宽   0px  ❌   （代码一个字没改）
```

→ **"让 2 帧就够"是个赌注**，布局何时完成取决于元素挂进去时处在帧的哪个相位。

**修**（`lib/cssprobe.js`）：
1. 基座量之前先给容器**预热**（自己先让两帧），把"首次延迟"这个变量隔离掉；
2. 新增 `settleUntil(predicate, maxFrames)` —— **轮询到为止**，并记录**用了几帧 / 耗时**；
   真机数据：`用了几帧=1　耗时=36ms`；
3. 所有几何探针从"等固定 2 帧"改成 `waitLaidOut()`（轮询到能给出非零几何）。

修后连跑三次，几何结论稳定，S9 回到 **9/14**（此前误报成 8/14）。

> **教训**（与 v0.2.1 那次同族，但更狠）：
> 上次是"量法错了"，这次是**判据错了**。判据错会**把自己的可信度一起抹掉** ——
> 「⚠️ 此结论不可信」这种标注一旦误报，人就会开始忽略它。
> 所以：**标注的可信度，和数据的可信度一样要自证。**

## 五、自证 · 以及**我没能自证的部分**（诚实清单）

| 命令入口 | manifest `Validate command successfull`（带 `shortcut` 也通过） |

### ⚠️ 没有自证（需要你，或需要更多场景）

1. **真实指针下的"不闪"**。我只能证明**几何不变量**（浮层不覆盖色块）与
   **状态机语义**（合成事件下幂等）。真实鼠标产生的 `mouseover/mouseout` 序列
   只有人手指能跑出来 → **请你在面板里来回划几下确认**。
2. **`Ctrl+Alt+F` 到底生效没有**（§3.6）。按一次就知道；不生效也不影响 `Alt+左键`。
3. **浮层会不会被滚动容器裁剪**。`getBoundingClientRect()` 给的是布局框，
   **不反映裁剪**。浮层在网格上方时贴着"品牌色"小标题，一般不会被裁；
   但如果你把面板滚动到网格顶到视口最上沿，浮层可能被切掉。
4. **填充在复杂文档上的表现**。自检只证明了"纯白文档能被精确填充"。
   文字图层 / 智能对象 / 锁定图层 / 32 位文档上的行为**没有覆盖**
   （代码会对"像素无变化"给出可读原因，但未逐一验证）。
5. **品牌 HEX 仍是占位色**（`tools/palette.js` 的 `DEFAULT_BRAND`，唯二阻塞项之一）。
